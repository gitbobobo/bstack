# bad-pattern-scan

找出 **agent 容易照抄、并已在多处重复出现** 的错误或不良编程模式。代码库就是 agent 的记忆：要用类型约束、lint、基础组件或重构把复发路径堵住，而不是再写一条会被忽略的文字规则。

在当前 harness 里由代理直接按本指引处理：用本环境已有的读代码、搜索、git 与检查工具查看仓库并整理结果。不要另起扫描启动器、命令行入口、批处理运行框架，也不要把通读交给外部 CLI 后端。

默认**只读**：只出带证据的中文报告，不创建 issue，不改被扫仓库，不提交，不联网发布。写入 Fast Ship 必须由本轮用户明确授权，规则见 [建单](references/filing.md)，执行时走 `$fast-ship`。

## 1. 范围、历史与证据基线

扫描对象以本轮用户指定的仓库、路径或方向为准；未指定则用当前工作区。本技能没有默认仓库清单。若一次范围内有多个仓库，每个仓库本轮最多报告 **一个** 新模式。

开始时记下仓库标识（如 `owner/name` 或本地显示名）和当时的 HEAD **SHA**。之后每条证据的路径与行号都以该 SHA 为准。需要对照历史版本时，用 git 在该 SHA 上读文件，不要凭记忆里的旧路径下结论。

先读可取得的历史，避免同仓同类再报一遍。历史来自本轮用户或调用方指定的历史文件，或调用方已有的状态；没有指定就不要假定某个本机路径。读法、去重和可选追加见 [历史](references/history.md)。指定了文件却解析失败时：停止写入、原样保留该文件，并向用户说明。

完成：范围、证据 SHA 和已读到的同仓历史已明确；建单默认关闭，除非用户在本轮明确授权。

## 2. 探索

按 [扫描准则](references/criteria.md) 自己读代码、搜索引用并推理，寻找「新代码会照着写」的重复错误。用户已指定方向就沿该方向。

查证时直接使用 harness 里的常规手段，例如 `git log` / `git show`、读源码、搜索引用、以及项目已有的测试或静态检查。这些是正常工具使用，不是另搞一套扫描运行器。命中只是线索，词法或 lint 命中不定罪。

不要把改 `AGENTS.md` 或其它规则文档当作改进建议。

## 3. 核实

每条拟报告的模式都要对照证据 SHA 抽查，并与历史和已有 issue 比较后再留下：

- **真实且够数：** 至少 3 处独立、真实的出现；文件在该 SHA 中存在，行号对得上，描述与代码一致。每处证据带固定 SHA + 路径 + 行号链接。凑不够 3 处、路径不存在、行号对不上、证据不足 → 丢弃。
- **是不良模式，不是合理异构：** 不能把本应不同的实现、有意的平台差异或只是长得像的代码算成同一模式。
- **会复发：** agent 或后续开发者容易照抄；代码库本身没有把它约束住。
- **改进可执行：** 建议是类型约束、lint / semgrep、基础组件封装或重构，落点明确。
- **与已有模式比较：** 对照历史里的同仓同类，以及能读到的既有 issue。已被覆盖的不要再当作新发现。

没有可信的新模式就不要凑。完成：进入报告的每条都经过核实；被丢弃的有内部原因，不必向用户逐条解释。

## 4. 报告

有可信新模式时，交付中文报告，每条写清：

1. **模式名称**
2. **证据**：证据 SHA，至少 3 处路径与行号链接
3. **影响**：为什么有害、为何容易被照抄
4. **改进**：可执行的约束或重构

若本轮新建了 issue，在报告中列出已建项目的编号与标题。

未找到可信新模式时不要凑报告：交互式调用按调用者要求说明（例如简短说本轮没有新模式）；自动或定时类调用若无新项则静默，不要发「扫了但没有发现」的摘要。

结论限定为「在所述范围和方法内发现或未发现」，不以找全问题为完成标准。

## 5. 可选建单

仅当本轮用户明确授权把通过核实的模式写成 Fast Ship issue 时，才按 [建单规则](references/filing.md) 执行，查询与写入一律走 `$fast-ship`。未授权则停在报告。不要把「做了坏模式扫描」或历史上某次授权理解成已经允许本轮建单。

若本轮确实新建了 issue：**只额外通知**项目名、编号与标题。自动或定时类调用没有新建则**静默**。

## 6. 可选追加历史

报告（以及授权时的建单尝试）完成后再按 [历史](references/history.md) 安全追加。只追加本轮已向用户报告的模式；创建失败不得记成已建，以免以后当成已建而不再补单。不要覆盖已有记录，也不要为了写历史去创建一套运行框架。
