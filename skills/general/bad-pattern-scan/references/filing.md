# 建单规则（默认关闭）

默认只读，不创建 issue。只有本轮用户明确授权把通过核实的模式建成 Fast Ship issue（例如「建单」「创建 issue」）时，才进入本节。缺授权就只出报告。不要把「做了坏模式扫描」或历史上某一次授权理解成已经允许本轮建单。

## 依赖

查询与创建一律按 `$fast-ship` 执行，不要在本技能里复制凭证或另写一套客户端。未安装 `$fast-ship`、或其外部配置尚未完成时：停止建单，保留只读报告，向用户说明需先安装该技能并完成其配置。禁止把密钥写进命令行、环境变量赋值、本技能文件或报告。

按 `$fast-ship`：API Key 不能关闭 issue，不能发评论。本技能建单后保持待办，不要自行关单或标完成。

项目按名称对齐，不要写死项目 UUID。若用户给出了项目名，就用该项目。代码仓库与 Fast Ship 项目已绑定的远端仓库可以不一致——以项目既有绑定为准，视为有意设置，不要改绑，也不要当成配置错误。

## 查重

对每一条准备建单的模式，按 `$fast-ship` 搜索对应项目的 issue，范围必须包括：

- 仍开放的 issue；
- 已关闭的 issue（同一主题不要再开一张）；
- 当天已经新建的 issue（含本轮前面刚创建的）。

可用该技能提供的查询（例如按标题、正文、`INT-xxx`、关键路径、模式名称或规范化类别）。已被覆盖的模式跳过，内部记下对应编号即可。历史里已经是「已建」（带有核验过的 issue 编号）的，不要再创建。历史里只是「已报」但尚未建单的，在本轮已获授权时可以补建，仍须先查重。

**每创建一张之前，再查一次**当天、同项目、同主题，避免连续创建撞车。

创建时来源为 internal，除非用户明确要求同步 GitHub。

## 文案

- 标题：中文，短而具体，能看出模式本身。
- 正文至少包含：

```markdown
## 问题

<模式说明：为何是不良模式、为何容易被照抄>

## 证据

- 仓库：<owner/name 或本地显示名> @ <证据 SHA>
- <带 SHA 的路径与行号链接>
- <至少 3 处>

## 影响

<会造成什么后果、若不约束会如何复发>

## 建议

<可执行机制：类型约束、lint / semgrep、基础组件封装或重构；写清落点>

## 验收标准

- [ ] <可检查的完成条件>

## 来源

- 日期：<YYYY-MM-DD，注明时区>
- 任务：坏模式扫描
```

「验收标准」可以按模式需要增补，但不要用它代替可执行的改进建议。正文不得包含密钥、token、服务地址或其它凭证，也不要建议靠改 `AGENTS.md` 或规则文档收尾。写完必须按 `$fast-ship` 回读标题与正文，确认是正常中文、不含 `U+FFFD` 或 `??`。只看接口成功不够。回读失败或内容不对视为创建失败，不得当作已建。

## 通知

只向用户报告**本轮新建**的项目名、编号（如 `INT-123`）和标题。自动或定时类调用没有新建则静默，不要列举跳过原因。
