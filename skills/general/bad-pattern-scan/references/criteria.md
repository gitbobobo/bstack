# 扫描准则

目标是找出 agent 容易照抄、并已在多处重复的不良编程模式，再给出能堵住复发路径的可执行改进。不要罗列一次性笔误、纯风格偏好或理论重构。

## 什么算

同一仓库内，同一种错误或不良写法已经在至少 3 处独立位点出现，并且后来的人（尤其是 agent）很可能会再抄一处。典型信号包括：

- 已经有基础组件、类型或辅助函数，业务代码仍直接走底层 API 或手写一份平行实现。
- 同一套易错逻辑（吞掉取消/错误、手拼标识、各写一份格式化或防抖等）在多个模块里复制，而且没有共同约束。
- 新代码只能靠照抄旧代码才能「写对」，代码库没有把正确做法变成默认路径。

每个仓库本轮最多留下 **一个** 模式。若有多个候选，保留证据最扎实、复发风险最高、改进落点最清楚的那一个。

## 什么不算

- 少于 3 处独立位点，或把同一函数、同一代码块里的相邻行拆开凑数。
- 合理的异构行为：不同平台/层本来就该不同的实现、有意的兼容分支、测试夹具、生成代码里的重复。
- 只是长得像、但意图或约束不同的代码。
- 一次性缺陷、纯命名或格式偏好、范围大到不可控的「整体重写」。
- 单靠再写一条 `AGENTS.md` 或规则文档就能「提醒下次注意」的建议——那不是本技能要的改进。

## 证据

对照本轮记下的 HEAD SHA 逐处核实：

- 文件在该 SHA 中存在，行号指向的代码确实体现该模式。
- 每处写成可点击的链接，或等价的「SHA + 路径 + 行号」：GitHub 上形如 `https://github.com/<owner>/<repo>/blob/<sha>/<path>#L<n>` 或 `#L<start>-L<end>`；其它托管或纯本地仓库同样写死 SHA、路径和行号，不要用浮动的分支名代替 SHA。
- 链接里的 SHA 必须是本轮证据基线，不要混用旧提交里的行号。
- 词法搜索、正则或 lint 命中只是线索，必须自己打开代码确认。

## 规范化类别

除了给人看的模式名称，再给一个短的 **规范化类别**，用来做同仓去重。类别要比「绕过封装」「手写重复逻辑」这类大桶更具体，具体到同一套机制、同一层或同一基础组件；也不要细到某一文件的某一次调用。

比较时看仓库 + 规范化类别（必要时再对照模式名称和摘要），不要只做标题字符串精确匹配。同类已在历史或既有 issue 里出现过，就不要再当作新发现。不同机制（即便同属「绕过已有封装」这种大主题）可以是不同类别，不互相屏蔽。

## 改进只给可执行机制

建议必须能在代码或工具链里落地，例如：

- **类型约束**：把正确入口做成唯一可编译路径，让错误用法难以通过类型检查。
- **lint / semgrep**：增加可自动执行的规则，拦住再抄底层 API 或禁用写法。
- **基础组件封装**：把正确实现收进已有或新建的共享组件，并让业务只走它。
- **重构**：删掉平行实现，把现有调用点迁到唯一入口。

写清落点（文件 / module / 规则位置）和可验收行为。不要建议靠更新 `AGENTS.md`、提示词或其它规则文档来防止复发。
