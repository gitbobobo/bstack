# bug-scan

找出生产代码里真实、可触发的 bug：逻辑错误、输入边界、错误处理、并发与资源、持久化与协议，以及鉴权、授权、注入和敏感信息等问题。只报能说清证据、生产可达调用链、前置条件，以及「输入如何得到错误结果」的发现。

在当前 harness 里由代理直接按本指引处理：用本环境已有的读代码、搜索、git 与检查工具查看仓库并整理结果。不要另起扫描启动器、命令行入口、批处理运行框架，也不要把通读交给外部 CLI 后端，或规定必须安装某一套工具或工具链。

默认**只读**：只出带证据的中文报告，不创建 issue，不改被扫仓库，不提交，不联网发布，也不为扫描安装依赖、工具链或运行会隐式写入、执行不受信构建脚本的命令。写入 Fast Ship 必须由本轮用户明确授权，规则见 [建单](references/filing.md)，执行时走 `$fast-ship`。

## 1. 范围与证据基线

扫描对象以本轮用户指定的仓库、路径或方向为准；未指定则用当前工作区。本技能没有默认仓库清单，也不要求一次扫完多个互不相关的仓库——用户点了几个就看几个。不要为扫描再克隆一份仓库，也不要规定扫完后删除本地副本。

开始时记下仓库标识（如 `owner/name` 或本地显示名）和当时的 HEAD **SHA**。之后每条发现的文件路径与行号都以该 SHA 为准。需要对照历史版本时，用 git 在该 SHA 上读文件，不要凭记忆里的旧路径下结论。

完成：范围和证据 SHA 已明确；建单默认关闭，除非用户在本轮明确授权。

## 2. 探索

按 [扫描准则](references/criteria.md) 探索。用户已指定方向就沿该方向；否则从入口（HTTP handler、RPC、CLI、UI 事件、生产会跑的定时或脚本任务）沿调用链查看，并优先读鉴权、支付、网络、持久化、并发、解析与 IPC 等较危险的区域，以及近期频繁改动的代码。

查证时直接使用 harness 里的常规手段，例如读源码、搜索引用、`git log` / `git show`，以及**当前环境里已经有的**、且能只读使用的静态检查。这些是正常工具使用，不是另搞一套扫描运行器。没有现成工具时，读代码即可，不要为跑本技能去安装工具、固定版本，或跑 `npm ci`、下载 SDK、启用 CodeQL 之类的重依赖。工具或规则命中只是线索，必须打开代码核对，并在报告里写明覆盖缺口。

## 3. 核实

每条拟报告的发现都要对照证据 SHA 抽查，并同时满足下面的门槛后才能留下：

- **真实：** 文件在该 SHA 中存在，行号对得上，描述与代码一致。路径不存在、行号对不上、证据不足 → 丢弃。
- **生产可达：** 能追到生产入口的调用链。测试、示例、生成代码、vendor 或第三方拷贝默认不当作生产，不报。脚本或运维文件若确实会在生产中运行，不得只因为后缀像脚本就排除。
- **触发说得清：** 写清前置条件，以及具体输入如何得到错误结果。说不清就不进入正式发现。
- **防护已核实：** 对照代码与框架语义核对已有校验、中间件、权限和错误处理；不要假设「大概有防护」。部署或运行环境未知时，把这一点标为限制，不要编造暴露面，也不要因此放过高置信逻辑错误。
- **安全项另有门槛：** 安全类发现必须有可信威胁模型和外部可控性说明。不要把非安全用途的哈希或普通随机（如展示用、checksum、非安全抖动）报成安全问题；也不可因为输入来自服务端，就机械丢掉真正的逻辑错误。
- **不是风格或理论题：** 纯风格、命名偏好、以及没有具体触发路径的理论异常，不报。

既达不到上述门槛、又仍有价值的线索，可列入低置信附录（最多 5 条待确认），**不建 issue**。

完成：进入报告的每条都经过核实；被丢弃的有内部原因，不必向用户逐条解释。

## 4. 报告

交互式审查按调用者需要交付中文报告，允许零发现。报告包含：

1. **范围**：仓库或路径、证据 SHA、本轮方向与方法；已使用的检查手段和未覆盖的方向（合理覆盖即可，不以找全为完成标准）。
2. **发现**：按严重级分组。每条写清：严重级、证据 SHA、文件路径与行号、问题、来源（规则/搜索/阅读）、前置条件、从输入到错误结果的触发、生产可达调用链、已核实的防护或框架语义（部署未知则写明限制）、建议修法、验收要点。可附受控、离线的最小复现指引；不得指导攻击线上系统或使用真实账户与数据。日志、密钥和其他敏感证据必须脱敏。
3. **低置信附录**（可选）：最多 5 条待确认线索，不作为建单对象。
4. **未纳入**：仅在有必要时用一两句概括跳过的方向或覆盖缺口，不要把未核实的线索写成结论。

结论限定为「在所述范围和方法内发现或未发现」。严重级按已核实的实际影响、可利用性和发生概率评定，规则见 [扫描准则](references/criteria.md)，不要按问题类型自动定为最高级。

## 5. 可选建单与通知

仅当本轮用户明确授权把通过核实、且值得跟进的高置信发现写成 Fast Ship issue 时，才按 [建单规则](references/filing.md) 执行，查询与写入一律走 `$fast-ship`。未授权则停在报告，不要把「做了 bug 扫描」理解成已经允许建单。低置信附录和证据不完整的条目不得建单。

若本轮确实新建了 issue：**只通知**项目名、编号与标题。没有新建则**静默**，不要发「扫了但没建单」的摘要。
