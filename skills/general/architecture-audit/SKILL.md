找出 architectural friction，提出 **deepening opportunities**（把浅 module 做成深 module），改善可测试性与 AI 可导航性。默认只读：只出报告，被扫仓库不改、不提交，不为审计安装依赖或工具。

## 1. 范围与基线

范围取用户本轮指定的仓库、路径或方向，缺省为当前工作区。记下仓库标识（`owner/name` 或本地名）和 HEAD **SHA**，路径与行号都以该 SHA 为准，旧版本用 `git show <SHA>:<path>` 读。

## 2. 探索

按 [审计准则](references/criteria.md) 探索。用户指定了方向就沿该方向；否则先看近期提交热点，再读 `CONTEXT.md` 与 ADR（若存在），然后有机地查看摩擦点。工具命中只是线索，打开代码核对过才算证据。

## 3. 核实

每条候选对照证据 SHA 抽查，同时满足才留下：

- **真实：** 文件、行号与描述在该 SHA 上对得上。
- **有收益：** 改善 locality、leverage 或测试面；纯风格、命名偏好、无证据的投机项跳过。
- **可控：** 落点明确（文件 / module / 可验收行为），整体重写不算。
- **未被覆盖：** 对照 ADR、已完成或进行中的同类深化、能读到的既有 issue 与先前报告；已覆盖、或与 ADR 冲突且不足以重开的，不算新发现。

**完成标准**：报告里每条候选都过了这四关。

## 4. 报告

中文报告，允许零发现：

1. **范围**：仓库、证据 SHA、方向与方法。
2. **候选**：按推荐强度 `Strong` / `Worth exploring` / `Speculative` 分组，每条写短名、`path:line`、问题（当前摩擦）、建议（深化方案）、收益（locality / leverage / 测试面）、验收要点。
3. **未纳入**：必要时一两句概括跳过的方向。

结论限定为「在所述范围和方法内发现或未发现」。
