# 改动准入

在把审查意见变成修复、独立 issue、后续 PR 或交接任务前使用。审查是线索；是否值得实施由需求、当前事实与收益决定。已有 issue、优先级标签、顾问赞同或空闲名额都不替代准入。

## 先证明问题，再选修法

1. **需求锚点**：找到用户要求、已确认设计或公共契约，写清必须交付与必须保留的行为。原始意见、作者回复和已否决方案一起读；代理写入的“共识”也须追溯授权依据，字段名不等于用户批准。新增功能、重构与文档改进也可由明确需求成立，不强求先有故障。
2. **当前证据**：在最新目标分支核对调用方与可达路径，说明谁在什么条件下受损，附复现、失败检查、日志或具体契约冲突。仅有假设输入、孤立常量或 mock 断言时，先做最小取证。安全、数据与并发高后果疑点优先调查，证据未明时保留风险状态，不能因低频直接忽略。
3. **净收益**：区分「问题成立」与「建议修法成立」。选能满足需求且守住原行为的最小方案，比较保持现状、删除无效改动、局部修复；成本包含新状态、维护、验证与回归风险。性能建议须有热路径或测量依据；单纯“更统一”“未来可能需要”只算候选。公共边界即使暂未观察到故障，也可用明确契约和可执行反例证明必要性。
4. **去向与去重**：回读来源 issue/PR 的当前状态与处置、最新目标分支及同根在途工作；来源已被用户以不采纳结案、撤销或驳回时保持停止，`in_progress` 等工作流字段不覆盖该决定；普通完成/合并不等于禁止报告新的真实缺陷。原 PR 仍开着且属同一交付，优先在原 PR 修；已合并的真实遗漏可独立修。另立项须有独立价值与验收条件，保留来源、裁决与原审查预算，换 PR 不重置同一问题的历史。

完成时，在已有 PR 描述、账本或 issue 中简记「需求/受损场景 → 证据 → 保留行为 → 处置」，链接原意见即可；不为准入另造表单或空 issue。

## UI 分支：保留设计意图

涉及外观、文案或交互时，在净收益判断前核对原需求、设计文档与实际状态：

- 出血/裁切、透明/玻璃、弱化层级、悬停提示与跨端差异可能是有意设计。截图只是状态采样；静止图不能证明悬停、动画或滚动末端不可达，跨端数值一致也不证明语义一致。跨端传播前先确认源修法已生效且适用于目标端，源方案被证伪则暂停其对齐任务。
- 对可读性、可达性或无障碍缺陷，确认受损的具体内容、控件和状态；测量目标像素/热区或实际驱动交互，区分主信息与有意弱化的装饰。确有缺陷仍须保留不相关的层级与操作。
- 基线与修后使用同一数据、位置和环境，覆盖改动触及的状态（例如当前/非当前/未开始行、滚动静止/末端、单行/双行）。目标本应产生可见变化却没有差异时，回查消费/渲染链；先证明生效，再扩大修法。纯函数测试不能代替可见结果。
- 未授权的用户可见语义或视觉方向变化，默认保留原设计。可选建议暂存或不采纳，继续当前交付；只有完成原任务必须作此决定时才向用户提出选择。顾问可以分析，不能替用户扩展需求。截图夹具、视口或测试环境造成的观感问题，先修证据，不直接改产品。

## 四种处置

| 结果 | 条件与动作 |
| --- | --- |
| 本次修复 | 问题、修法与授权均成立，属于当前交付；按分级与预算实施并验证 |
| 独立交付 | 同样已准入，但有独立职责、已合并后遗漏或明确后续需求；给可验收边界，再建 issue/PR 或交接 |
| 暂存候选 | 证据不足、收益未定或缺产品决定；在现有记录写缺口与重启条件，自动派活跳过，不阻塞当前任务收尾；原任务必需的决定才交用户 |
| 不采纳 | 误报、保留的设计、不可达假设、已解决/重复，或收益不抵风险；写依据后结束，不生成执行任务 |

nit 不是待履行的承诺。「记录后续」默认是随相关需求再评估，只有通过上述准入的事项才进入执行队列。没有可准入工作时，空位留空。
