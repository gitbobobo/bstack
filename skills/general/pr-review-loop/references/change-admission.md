# 本 PR 改动准入

在决定是否将审查意见改进当前 PR 时使用。这里判断“本 PR 为交付原始意图还需要改什么”，不裁决独立任务是否值得自动派活。范围外建议可记录目标与事实，交独立任务流程评估；本 PR 接受不修不等于永久否决。

## 核问题、修法与交付范围

1. **意图锚点**：找到本任务的用户要求、已确认设计或公共契约，写清必须交付与必须保留的行为。原始意见、作者回复和已否决方案一起读；代理写入的“共识”须追溯授权依据。
2. **当前证据**：核意见声称的问题是否存在。行为缺陷核调用方、可达路径与复现、日志或契约证据；原任务本身是功能或架构改进时，按其交付与验收目标核缺项，无需先有故障。安全、数据与并发高后果疑点优先取证，证据未明时保留风险状态。
3. **修法与范围**：区分问题成立与建议修法成立，比较修法的行为影响、维护及回归成本。意图内意见进入技能的分级与预算；范围外意见记录事实与建议目标，继续当前交付。新增技术方案由实现线程决定，未授权的产品语义改变另行分流。
4. **历史与去重**：核问题是否已解决、用户是否否决、同一交付是否已有在途修复。换 PR 续办同一未完成交付保留其来源与审查历史；独立任务的价值、排期与可执行性由对应任务流程判断。

完成时，在 PR 描述、账本或现有 issue 中简记“意图 → 证据 → 保留行为 → 本 PR 处置”，链接原意见即可。

## UI 分支：保留设计意图

涉及外观、文案或交互时，在判断修法前核对原需求、设计文档与实际状态：

- 出血/裁切、透明/玻璃、弱化层级、悬停提示与跨端差异可能是有意设计。截图只是状态采样；静止图不能证明悬停、动画或滚动末端不可达，跨端数值一致也不证明语义一致。跨端传播前先确认源修法已生效且适用于目标端，源方案被证伪则暂停其对齐任务。
- 对可读性、可达性或无障碍缺陷，确认受损的具体内容、控件和状态；测量目标像素/热区或实际驱动交互，区分主信息与有意弱化的装饰。确有缺陷仍须保留不相关的层级与操作。
- 基线与修后使用同一数据、位置和环境，覆盖改动触及的状态（例如当前/非当前/未开始行、滚动静止/末端、单行/双行）。目标本应产生可见变化却没有差异时，回查消费/渲染链；先证明生效，再扩大修法。纯函数测试不能代替可见结果。
- 未授权的用户可见语义或视觉方向变化，默认保留原设计。可选建议记录后继续当前交付；只有完成原任务必须作此决定时才向用户提出选择。顾问可以分析，不能替用户扩展需求。截图夹具、视口或测试环境造成的观感问题，先修证据，不直接改产品。

## 本 PR 的处置

| 结果 | 条件与动作 |
| --- | --- |
| 本次处理 | 问题与修法成立，属于本 PR 交付；按分级与预算实施或书面接受 |
| 范围外建议 | 记录目标、已知事实与未核项，供独立任务流程评估；不因另建 issue 延长当前审查 |
| 待核 | 意图内关键事实未明，做定向取证后再判；潜在高后果风险未明时暂缓合并 |

nit 不构成本 PR 的待履行义务。记录后续也不构成新任务的自动执行承诺；独立派活另按其任务标准判断。
