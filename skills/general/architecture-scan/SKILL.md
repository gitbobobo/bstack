# architecture-scan

找出 architectural friction，提出 **deepening opportunities**（把浅 module 做成深 module），改善可测试性与 AI 可导航性。

在当前 harness 里由代理直接按本指引处理：用本环境已有的读代码、搜索、git 与检查工具查看仓库并整理结果。不要另起扫描启动器、命令行入口、批处理运行框架或把通读交给外部 CLI 后端。

默认**只读**：只出带证据的中文报告，不创建 issue，不改被扫仓库，不提交，不联网发布。写入 Fast Ship 必须由本轮用户明确授权，规则见 [建单](references/filing.md)，执行时走 `$fast-ship`。

## 1. 范围与证据基线

扫描对象以本轮用户指定的仓库、路径或方向为准；未指定则用当前工作区。本技能没有默认仓库清单，也不要求一次扫完多个互不相关的仓库——用户点了几个就看几个。

开始时记下仓库标识（如 `owner/name` 或本地显示名）和当时的 HEAD **SHA**。之后每条候选的文件路径与行号都以该 SHA 为准。需要对照历史版本时，用 git 在该 SHA 上读文件，不要凭记忆里的旧路径下结论。

完成：范围和证据 SHA 已明确；建单默认关闭，除非用户在本轮明确授权。

## 2. 探索

按 [扫描准则](references/criteria.md) 探索。用户已指定方向就沿该方向；否则先看近期提交热点，再读相关的 `CONTEXT.md` 与 ADR（若存在），然后有机地查看摩擦点。

查证时直接使用 harness 里的常规手段，例如 `git log` / `git show`、读源码、搜索引用、以及项目已有的测试或静态检查。这些是正常工具使用，不是另搞一套扫描运行器。命中只是线索，词法或 lint 命中不定罪。

不要把 HTML 架构报告或交互式 grilling 当作默认产出。本轮是扫描与核实，不是开工重构。

## 3. 核实

每条拟报告的候选都要对照证据 SHA 抽查，并与已有模式比较后再留下：

- **真实：** 文件在该 SHA 中存在，行号对得上，描述与代码一致。路径不存在、行号对不上、证据不足 → 丢弃或降级。
- **有收益：** 能改善 locality、leverage 或测试面。纯风格、命名偏好、无热路径证据的投机项、或范围大到不可控的项默认跳过。
- **可控：** 建议有明确落点（文件 / module / 可验收行为），不是整体重写。
- **与已有模式比较：** 对照已有 ADR、代码里已完成或进行中的同类深化、以及能读到的既有 issue 或先前报告。已被覆盖或与 ADR 冲突且不足以重开的，不要再当作新发现。

完成：进入报告的每条都经过核实；被丢弃的有内部原因，不必向用户逐条解释。

## 4. 报告

交付中文报告，允许零发现。报告包含：

1. **范围**：仓库或路径、证据 SHA、本轮方向与方法。
2. **候选**：每条写清短名、推荐强度（`Strong` / `Worth exploring` / `Speculative`）、证据 SHA、文件路径与行号、问题（当前摩擦）、建议（深化方案）、收益（locality / leverage / 测试面）、验收要点。
3. **未纳入**：仅在有必要时用一两句概括跳过或未完成的方向，不要把未核实的线索写成结论。

结论限定为「在所述范围和方法内发现或未发现」，不以找全问题为完成标准。

## 5. 可选建单与通知

仅当本轮用户明确授权把通过核实的候选写成 Fast Ship issue 时，才按 [建单规则](references/filing.md) 执行，查询与写入一律走 `$fast-ship`。未授权则停在报告，不要把「做了架构扫描」理解成已经允许建单。

若本轮确实新建了 issue：**只通知**项目名、编号与标题。没有新建则**静默**，不要发「扫了但没建单」的摘要。
