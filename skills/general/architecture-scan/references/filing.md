# 建单规则（默认关闭）

默认只读，不上报、不创建 issue。只有同时满足下列条件才进入本节：

1. 本轮用户明确授权把通过核实的候选建成 Fast Ship issue（口头或书面「建单」「创建 issue」等）；
2. 本地配置里 `fast_ship.enabled` 为 `true`（见 [配置示例](config.example.yaml)）。

缺任一条件都只出报告。不要把「跑了架构扫描」理解成已经授权建单。

## 依赖

建单走已安装的 **fast-ship** 技能：调用 `node <fast-ship 技能目录>/scripts/fast-ship-api.mjs`，请求体写成 UTF-8 JSON 文件，按该技能要求回读。本仓库已收录该技能时，路径为 `skills/services/fast-ship`。

- 不要在本技能中复制 API key、服务地址或另写一套客户端。
- 凭证只存在于 fast-ship 的外部配置。本技能的配置文件不得包含 `api_key`、token 或 base URL。
- 未安装 fast-ship、或其外部配置不存在时：停止建单，保留只读报告，向用户说明需先安装该技能并完成其外部配置。禁止把密钥写进命令行、环境变量赋值或输出。
- 按 fast-ship 技能：API Key 不能关闭 issue，不能发评论。本技能建单后保持待办，不要自行关单或标完成。

项目用 `GET /api/projects` 按名称对齐，不要写死项目 UUID。代码仓库与 Fast Ship 项目已绑定的远端仓库可以不一致——以项目既有绑定为准，视为调用方有意设置，不要改绑，也不要当成配置错误。名称映射可写在本地配置的 `fast_ship.projects`（扫描目标名 → 项目名）。

## 查重

对每一条准备建单的候选，搜索对应项目的 issue，范围必须包括：

- 仍开放的 issue；
- 已关闭的 issue（同一主题不要再开一张）；
- 当天已经新建的 issue（含本轮前面刚创建的）。

查询可用项目 issue 列表的 `q`（标题、正文、`INT-xxx` 等）。按候选标题、关键路径、短名搜索。已被覆盖的候选跳过，内部记下对应编号即可。

**每创建一张之前，再查一次**当天、同项目、同主题，避免连续创建撞车。

创建时 `source` 为 `"internal"`，除非用户明确要求同步 GitHub。

## 文案

- 标题：中文，短而具体，能看出深化对象。
- 正文至少包含：

```markdown
## 现状
- 仓库：<owner/name 或本地显示名> @ <证据 SHA>
- 文件：
  - `path`（约第 N 行）

## 问题

<摩擦与证据>

## 建议

<深化方案>

## 收益

- <locality / leverage / 测试面等>

## 验收标准

- [ ] <可检查的完成条件>

## 来源

- 日期：<YYYY-MM-DD，注明时区>
- 任务：架构扫描
```

正文不得包含密钥、token、服务地址或其它凭证。写完必须回读标题与正文，确认是正常中文、不含 `U+FFFD` 或 `??`。只看接口成功不够。

## 通知

只向用户报告**本轮新建**的项目名、编号（如 `INT-123`）和标题。没有新建则静默，不要列举跳过原因。
