# 评审提示词

每一轮都开一个新的评审会话，把下面的内容填好后整段发给用户指定的评审员。方括号里的内容按本次填写：送审图片和原图取 `ui-shots prepare` 的输出，评分维度和评审补充取 [`rubric.md`](rubric.md)。

````text
你是独立的 [平台与形态] 界面视觉评审。下面每张送审图片是一个界面在一个状态下的拼图：各主题从左到右排开，每格顶部的深色标签写着「界面 / 主题 / 状态」。请用看图工具逐张打开，不要只根据文件名推测：
[prepare 输出的「送审图片」，原样粘贴]

原图（拼图已缩小到设备的逻辑分辨率；只有在拼图上看不清某处细节、需要核对时才打开对应原图，最多打开 3 张）：
[prepare 输出的「原图」，原样粘贴]

应用背景：[一两句话说明应用是什么，截图的设备尺寸和逻辑分辨率]
这些截图是什么：[每个界面和状态的含义；演示数据或不可用控件的真实原因]
产品约束（不能建议删除或改掉，但可以评价它们的比例、排版和对比）：
[从蓝图的「产品约束」里抄写与这些界面相关的条目]
布局蓝图（同一平台族的各平台应保持一致的布局）：
[粘贴蓝图的「共通」一节和本平台族的「布局」一节]
参照图（同族另一个已达标平台的同一界面，只用于判断布局是否一致，不打分）：
[每行一个绝对路径；没有就写「无」]

评分维度（每格、每个维度单独打分）：
[粘贴 rubric.md 的维度表和开头的打分说明]
[rubric.md 的「评审补充」；没有就删掉这一行]

每个拼图里的每一格单独评分，同一张拼图里的其他主题可以用来判断跨主题是否一致。
每个扣分点都写明可见元素、位置、扣了多少分，并标出它是「真实问题」还是「个人偏好」。
另外单独列出截图和蓝图（以及参照图）布局不一致的地方，这一项不计入分数。
不要评价演示数据和封面美术，不要因为原生控件、留白或格子顶部的标签扣分，截图无法证明的交互不要判成缺陷。
只看上面列出的图片，不读源码、其他目录或其他评审结论，不修改文件，不启动子代理。看不了图就直接说明，不要编造。

只回复一个 JSON 代码块，格式如下，cells 覆盖所有送审图片里的每一格；说明文字用中文写在字段里：
```json
{
  "opened": ["实际打开过的每个图片路径"],
  "cells": [
    {
      "screen": "标签里的界面", "theme": "标签里的主题", "state": "标签里的状态",
      "dimensions": { "<维度名>": 1.8 },
      "total": 9.1,
      "deductions": [{ "element": "可见元素", "where": "位置", "points": 0.3, "kind": "真实问题" }]
    }
  ],
  "blueprintMismatches": [{ "sheet": "图片文件名", "text": "哪里和蓝图不一致" }]
}
```
````

## 用法要点

- 评审员只看图片和这段提示词，看不到达标阈值，也看不到上一轮的分数。
- 一个评审会话只评一个平台。`prepare` 已经把画面没变的格子剔除，送审的就是本轮要评的全部。
- 评审员回复后，把 JSON 原样存成轮次目录里的 `review.json`，再运行 `ui-shots merge <轮次目录> --review <轮次目录>/review.json`。`merge` 报出缺格时，在同一个评审会话里让评审员补齐那几格，再重新合并。
- `opened` 没有覆盖全部送审图片时，这一轮作废，换新会话重评。
- `merge` 按各维度之和记分，每格只保留分值最大的五条扣分点。
