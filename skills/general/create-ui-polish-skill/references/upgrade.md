# 升级已有的 ui-polish-&lt;app&gt;

仓库里已经有 `ui-polish-<app>/` 时，按下面的步骤把它对齐到本技能的当前版本。文件归属见 [`SKILL.md`](../SKILL.md) 第 5 步的表：归本技能的文件直接覆盖，归仓库的文件保留内容、只对齐结构。地图数据向后兼容：旧分数没有 `shot` 字段也能照常读写，只是第一轮评审时没法沿用。

### 1. 读现状

读生成技能的 `SKILL.md`、`rubric.md`、`config.json` 和截图工具。用 `git log -- <技能目录>` 看它生成以来的提交，分清哪些内容是仓库后来加的。

完成标准：能说出仓库在模板之外加了哪些段落、哪些要求。

### 2. 覆盖本技能维护的文件

原样复制 `map-format.md`、`assets/`、`scripts/ui-map.mjs`、`scripts/ui-shots.mjs`，然后运行 `ui-map check`。

完成标准：这些文件和本技能里的一致，`check` 没有错误。

### 3. 迁移评审提示词

评审提示词现在由 `ui-shots prepare` 用 `assets/` 里的模板生成，`rubric.md` 原样拼进去。旧版的提示词可能在 `rubric.md` 的「评审提示词」「用法要点」两节，也可能在单独的 `review-prompt.md`。

- `rubric.md` 保留维度表和开头的打分说明，仓库改过的维度照旧保留。
- 旧提示词和新模板逐句对照：模板原有的句子带方括号占位，或者在新模板里有对应的句子；剩下的就是仓库加的要求，搬进 `rubric.md` 的「评审补充」。旧提示词里填过的应用背景、演示数据说明也搬进「评审补充」。
- 删掉 `rubric.md` 里的这两节和旧的 `review-prompt.md`，`SKILL.md` 里指向它们的地方按第 4 步改成新模板的写法。

完成标准：`rubric.md` 只剩维度和「评审补充」，仓库加过的每条要求都有了去处，技能目录里不再有 `review-prompt.md`。

### 4. 按模板对齐 SKILL.md

把 [`project-skill.md`](project-skill.md) 当作新版本，逐节比对生成的 `SKILL.md`：

- 模板的固定文字（`{{}}` 以外）以模板为准改写，包括新增的段落和改过的步骤。
- `{{}}` 的位置保留仓库已经填好的内容；模板新增的 `{{}}` 按 SKILL.md 第 1 步的做法从仓库里找答案填上。
- 仓库自己加的段落保留。它和新模板冲突时以新模板为准，把冲突列进汇报。
- 「截图」一节：按模板开头的三条要求（写清单、就绪断言、稳定）核对仓库的截图工具，缺哪条就在工具里补哪条，再把做法写进这一节。

完成标准：每一节都能对应到模板的某一节或某个仓库自加段落，目录里搜不到 `{{`。

### 5. 对齐蓝图

按 SKILL.md 第 4 步核对已有蓝图，已有的约束、打磨范围和决定记录不动：

- 「布局」一节还是笼统描述，或者写着「由本族第一个打磨的平台写实」这类等待后来者决定的话时，改写成本族现有实现：逐个界面写到区块的顺序和相对位置。已经打磨过的界面以当前代码为准。
- 从代码里找评审员容易误判的设计，补进「产品约束」，注明出处文件。
- 把仓库设计文档里的确认决定补进「产品约束」或「布局」，注明出处。

还没有 `### 打磨范围：<界面>` 的界面，下次打磨时会自动走定调轮，这里不替用户起草。

完成标准：每张蓝图的每节布局都写出了所覆盖界面的区块顺序，新增的每条约束都有出处。

### 6. 跑通一次

请用户指定评审员。按 SKILL.md 第 7 步走一遍，只做一个界面、只截本机平台，包括不改代码连拍两轮、用 `compare` 比较那一步。

完成标准：同 SKILL.md 第 7 步。

### 7. 汇报

- 覆盖了哪些文件；
- 从旧提示词迁进「评审补充」的要求；
- `SKILL.md` 里和新模板冲突的仓库段落，以及怎么处理的；
- 截图工具补了什么，哪些平台未在本机验证，哪些平台做不到稳定；
- 改写的布局和新增的产品约束；
- 第 6 步的结果。
