# ui-polish-{{app}}

{{App}} 的界面地图和打磨流程。本目录里：

- `config.json`：达标阈值、每批数量、平台、平台族、主题{{、页面注册表}}。
- `screens/<id>.json`：每个界面的状态、源码路径和各格分数，字段见 [`map-format.md`](map-format.md)。
- `blueprints/<名字>.md`：一组界面的布局蓝图。
- [`rubric.md`](rubric.md)：评分维度和评审提示词。
- `scripts/ui-map.mjs`：读写地图的唯一入口，`node scripts/ui-map.mjs --help` 查看命令。下文的 `ui-map` 都指 `node {{本目录相对仓库根的路径}}/scripts/ui-map.mjs`。

布局相近的平台归为一个平台族（`config.json` 的 `families`）：{{列出本仓库的平台族，例如 desktop = macOS、Windows、Linux、Web、鸿蒙电脑；phone = iPhone、Android 手机、鸿蒙手机；tablet = iPad、Android 平板、鸿蒙平板；tv = tvOS、Android TV；watch = watchOS、Wear OS、鸿蒙手表}}。蓝图的「共通」一节（信息结构、状态、产品约束）全应用一致；每个平台族有自己的「布局」一节，同族平台按它对齐，不同族之间不要求布局相同。

哪个平台先打磨某个界面，就由它写实本族的布局；同族其他平台按它对齐。改方向时先改蓝图，并在「决定记录」里写明理由。

### 蓝图改动与过期

蓝图改动不会自动让分数过期。改完蓝图，先看改的是哪一节，再判断哪些平台受影响：

- 改了某个平台族的「布局」：只可能影响同族的平台。
- 改了「共通」：可能影响所有平台族。

然后逐个判断受影响范围内的平台，现有界面还符不符合新蓝图：

- **不符合**：比如区块顺序变了、主操作换了位置、某个状态多了或少了元素。对受影响的界面、平台、状态运行 `ui-map invalidate <界面>... --platform <平台> [--state <状态>] --reason <改了什么>`。整组界面都受影响时用 `--blueprint <名字>` 代替界面列表；整族平台都受影响时用 `--family <族>` 代替平台列表。
- **仍然符合**：比如措辞调整、补充已经成立的产品约束、追加决定记录，或者在「族内允许的差异」里登记某个平台自己的做法。这些情况不标记过期。
- **发起改动的平台**：本轮会重新评分，`record` 会覆盖旧分数，不需要标记。

拿不准某个平台是否受影响时，就标记过期。多评一次的代价，比带着偏离继续发布小。

## 修改界面之后

新增、修改、删除界面的提交里同时更新地图：

1. 新增界面或状态：{{有注册表时：先登记到注册表，再运行 `ui-map sync-registry`。}}在 `screens/<id>.json` 里补全 `states`、`sources`、`blueprint` 和 `priority`。新状态截不到时，按「截图」一节补好截图入口；补不了就写进 `gaps` 并注明原因。
2. 删除界面：从地图里删掉对应文件{{，注册表按它自己的规则处理}}。某个平台不再提供：写进 `unsupported`。
3. 改动改变了蓝图描述的布局或状态：同一提交里改蓝图，追加「决定记录」，并按「蓝图改动与过期」处理其他平台的分数。
4. 运行 `ui-map check`。完成标准：没有「错误」，也没有「注册表里有，地图里没有」。「已过期」的提示是正常的，这些格子下次打磨时会被挑中，不需要当场重新评分。

## 打磨一批

1. **确认评审员和参数。** 评审员由用户在本次请求里指定（模型、harness 或渠道）。没指定时先请用户指定，指定前不开始评分。阈值和每批数量取 `config.json`。用户在本次给了新值时，运行 `ui-map config threshold <值>` 或 `ui-map config batchSize <值>` 保存下来，随本次提交。
2. **挑界面。** 运行 `ui-map next --platform {{本机负责的平台}}`。{{本机负责哪些平台：按仓库 AGENTS.md 的设备与平台对应规则确定，或写「全部平台」。}}输出就是这一批的界面和每一格的现状，按平台族分组，并列出同族已达标的「参照」平台，不需要再读整张地图。
3. **截图。** 按「截图」一节，截下这批界面在本机平台上的每一格：每个主题 × 每个状态。`gap` 格先补截图入口、删掉 `gaps` 条目，再截图。截图放在仓库外，逐张打开确认截到的是对应状态。本机也能截参照平台时，把参照平台的同一组状态一并截下，作为对齐用的参照图，不参与评分。完成标准：`next` 列出的每一格都有对应截图。
4. **评审。** 用 [`rubric.md`](rubric.md) 的提示词开一个新的评审会话，带上蓝图的「共通」一节、本族的「布局」一节，以及参照图（如果有）。不告诉评审员阈值。
5. **修改。** 先改真实问题，再看个人偏好。建议和蓝图冲突时，只有两种做法：不采纳；或者改蓝图并写明理由，再按「蓝图改动与过期」标记受影响的平台。改某个平台族的布局等于改了本族所有平台的方向，改「共通」等于改了所有平台族的方向，用户明确提出的产品决定才这样做。评审员指出的「与蓝图不一致」默认按蓝图改回来。
6. **复评。** 重新截图，开新的评审会话再评。一个界面所有格都达到阈值就停。连续两轮最低分的提升都不到 0.3 分，也停下来，把卡住的原因写进汇报。
7. **记录。** 先提交界面改动和蓝图改动。然后对每一格运行 `ui-map record <界面> --platform <平台> --theme <主题> --state <状态> --score <总分> --deduction <扣分点>`，扣分点可以重复给。新确认的产品约束写进蓝图。最后提交地图。只记录每格最后一轮的分数。
8. **汇报。** 列出每个界面打磨前后的最低分、仍未达标的格子和原因、补上的截图入口，以及 `ui-map status --platform <本机平台>` 的汇总。
