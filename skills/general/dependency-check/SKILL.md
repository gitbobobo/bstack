# dependency-check

核对仓库里**实际存在的生态**中的**直接依赖**：区分声明范围与锁定的解析版本，向对应 registry 查询最新稳定版，并按「立即升级 / 可以升级 / 暂不动」分档。查不到的标为未核验（unchecked），不要编造版本或漏洞。

在当前 harness 里由代理直接按本指引处理：用本环境已有的读文件、搜索、git 与只读查询手段查看仓库并整理结果。不要另起扫描启动器、命令行入口、批处理运行框架，也不要把通读交给外部 CLI 后端，或规定必须安装某一套工具。

默认**只读**：只出带证据的中文报告，不创建 issue，不改被扫仓库的代码、清单或 lockfile，不提交，不联网发布，也不安装或升级任何包。写入 Fast Ship 必须由本轮用户明确授权，规则见 [建单](references/filing.md)，执行时走 `$fast-ship`。

## 1. 范围与证据基线

扫描对象以本轮用户指定的仓库、路径或方向为准；未指定则用当前工作区。本技能没有默认仓库清单，也不要求一次扫完多个互不相关的仓库——用户点了几个就看几个。

开始时记下仓库标识（如 `owner/name` 或本地显示名）和当时的 HEAD **SHA**。清单、锁文件与版本结论都以该 SHA 为准。需要对照历史版本时，用 git 在该 SHA 上读文件，不要凭记忆里的旧路径或过期报告下结论。

完成：范围和证据 SHA 已明确；建单默认关闭，除非用户在本轮明确授权。

## 2. 探索

按 [扫描准则](references/criteria.md) 和 [生态与查询](references/ecosystems.md) 探索。用户已指定生态或包就沿该方向；否则先盘点该 SHA 下实际存在的清单与锁文件，再只对出现过的生态核对其直接依赖。

查证时直接使用 harness 里的常规手段，例如读清单与 lockfile、搜索引用，以及**当前环境里已经有的**包管理工具或 HTTP 查询——且必须是不会改写工作区的只读用法。这些是正常工具使用，不是另搞一套扫描运行器。环境没有某工具就换读文件和公开 registry 查询，不要为跑本技能去安装工具、登录私有源或固定版本。

registry 访问失败或私有源无法在不绕过授权的前提下查询时，将该项标为未核验，不要编造 latest，也不要泄漏认证信息。

## 3. 核实

每条拟写入报告的结论都要对照证据 SHA 抽查，并同时满足下面的门槛后才能留下：

- **范围真实：** 包确实出现在该 SHA 的清单或锁文件中；写清声明范围与锁定的解析版本（没有锁文件就如实写「无锁」，不要把范围当成已解析版本）。不要把间接依赖算成直接依赖，也不要把工具插件、构建依赖、工作区内部包或版本目录/BOM/constraints 与运行时直接依赖混成一列。
- **版本真实：** 最新稳定版来自本轮实际查询到的 registry（注明抓取日期、时区与 URL 或查询方式）。查不到、超时、私有源未授权 → 未核验。禁止把预发布版当成 latest stable，除非项目已经在跟预发布线，并在结论里写明。
- **漏洞与弃用有权威来源：** 安全结论必须能指向官方公告、OSV、GHSA 或同等权威通告，并核对该通告的受影响区间是否覆盖**实际锁版本**、修复版本是什么。过期或弃用必须有权威来源。不得把「落后几个大版本」或星标、下载量当成安全性证据。
- **分档站得住：** 按准则分档。跨多个大版本不能自动列为「立即升级」，必须同时说明明确收益和迁移成本；建议给出最小修复版本和可行目标，不要盲追 latest。
- **不改仓库：** 核实过程不得安装、升级包，不得改清单或 lockfile，并避开会隐式写入的命令。

完成：进入报告的每条都经过核实；被丢弃或未核验的有内部原因。未覆盖的生态必须在报告里显式列出，不能声称全覆盖。

## 4. 报告

交付中文报告，允许零发现（例如全部为「暂不动」或本轮范围内没有可核对的依赖）。用按生态分组的表格，不要再要求输出一套机器 JSON 协议。旧字段 `package` / `current` / `latest` / `ecosystem` / `bucket` 分别对应当前的包名、锁版本（或声明范围）、最新稳定版、生态和分档。

报告包含：

1. **范围**：仓库或路径、证据 SHA、本轮覆盖的生态与清单/锁文件，以及未覆盖或未能核对的部分。
2. **结论表**：按生态分组。每行尽量写清：包与声明范围、锁版本、最新稳定版、建议版本（最小修复或可行目标）、分档、证据、约束（如 MSRV / SDK / runtime / 平台 / 许可证 / peer）、升级验证建议。git / path / vendor 等无 registry 的依赖单列，不要伪造 latest。
3. **分档摘要**：立即升级、可以升级、暂不动、未核验的要点；立即升级项写清依据（漏洞、弃用，或落后一个以上大版本且已说明收益与迁移成本）。
4. **未纳入**：仅在有必要时用一两句说明跳过的间接依赖、未覆盖生态或未核验原因，不要把猜测写成结论。

结论限定为「在所述范围和方法内的核对结果」。在线来源一律注明抓取日期（含时区）和 URL 或查询方式。

## 5. 可选建单与通知

仅当本轮用户明确授权把通过核实、且有实际价值的项写成 Fast Ship issue 时，才按 [建单规则](references/filing.md) 执行，查询与写入一律走 `$fast-ship`。未授权则停在报告，不要把「做了依赖检查」理解成已经允许建单。未核验、证据不足或只是常规可升级而没有明确价值的条目不得建单。

若本轮确实新建了 issue：**只通知**项目名、编号与标题。没有新建则**静默**，不要发「扫了但没建单」的摘要。
