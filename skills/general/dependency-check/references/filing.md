# 建单规则（默认关闭）

默认只读，不创建 issue。只有本轮用户明确授权把通过核实的、有实际价值的项建成 Fast Ship issue（例如「建单」「创建 issue」）时，才进入本节。缺授权就只出报告。不要把「做了依赖检查」理解成已经允许建单。未核验、证据不完整、或只是常规可升级而没有明确价值的条目不得建单。

只建高置信、有价值的项：已核实的立即升级，或用户明确要求跟踪的、收益和动作都说得清的可以升级。不要把整张「可以升级」表都开成 issue。

## 依赖

查询与创建一律按 `$fast-ship` 执行，不要在本技能里复制凭证或另写一套客户端。未安装 `$fast-ship`、或其外部配置尚未完成时：停止建单，保留只读报告，向用户说明需先安装该技能并完成其配置。禁止把密钥写进命令行、环境变量赋值、本技能文件或报告。

按 `$fast-ship`：API Key 不能关闭 issue，不能发评论。本技能建单后保持待办，不要自行关单或标完成。

项目按名称对齐，不要写死项目 UUID。若用户给出了项目名，就用该项目。代码仓库与 Fast Ship 项目已绑定的远端仓库可以不一致——以项目既有绑定为准，视为有意设置，不要改绑，也不要当成配置错误。

## 拆分与合并

按仓库整理待建项。同一仓库、同一类可一起完成的立即升级（例如同一把锁上、同一修复路径的安全补丁刷新）可以合并成一张清单 issue。不要把需要独立处理的不同风险混在一张单里，例如：

- 已核实的安全修复与一次跨多个大版本的迁移；
- 修复路径、验证方式或约束明显不同的包；
- 直接依赖与需要单独决策的间接依赖；
- 一个可立即升级的包和一条仍属「上游阻塞 / 跟踪」的通告。

## 查重

对每一张准备创建的 issue，按 `$fast-ship` 搜索对应项目的 issue，范围必须包括：

- 仍开放的 issue；
- 已关闭的 issue（同一主题不要再开一张）；
- 当天已经新建的 issue（含本轮前面刚创建的）。

可用该技能提供的查询（例如按标题、正文、`INT-xxx`、包名、生态或通告编号）。已被覆盖的项跳过，内部记下对应编号即可。

**每创建一张之前，再查一次**当天、同项目、同主题，避免连续创建撞车。

创建时来源为 internal，除非用户明确要求同步 GitHub。

## 文案

- 标题：中文，短而具体，能看出是依赖升级或哪一类风险（例如某包的安全修复，或某一批可一并刷新的补丁）。
- 正文至少包含：

```markdown
## 现状

- 仓库：<owner/name 或本地显示名> @ <证据 SHA>
- 生态与包：
  - `<生态>` `<包>`：声明 `<范围>`，锁版本 `<锁版本>`，最新稳定版 `<latest>`，建议 `<建议版本>`

## 证据

- <通告编号与 URL，或弃用来源，或跨大版本的收益依据>
- <受影响区间是否覆盖锁版本、修复版本是什么；在线来源的抓取日期（含时区）>

## 影响

- <不升级会怎样；约束与迁移成本>

## 建议

- <最小修复版本或可行目标；不要盲追 latest；需要改清单还是只刷新锁>

## 验收标准

- [ ] <锁版本离开受影响区间或到达建议版本>
- [ ] <相关测试或构建已按建议路径验证>

## 来源

- 日期：<YYYY-MM-DD，注明时区>
- 任务：依赖检查
```

正文不得包含密钥、token、服务地址或其它凭证。写完必须按 `$fast-ship` 回读标题与正文，确认是正常中文、不含 `U+FFFD` 或 `??`。只看接口成功不够。回读失败或内容不对视为创建失败，不得当作已建。

## 通知

只向用户报告**本轮新建**的项目名、编号（如 `INT-123`）和标题。没有新建则静默，不要列举跳过原因。
