# 扫描准则

目标是给出带证据的依赖分档，而不是罗列「有更新」，也不是自动追最新版。

## 分档

| 分档 | 何时使用 |
| --- | --- |
| **立即升级** | 实际锁版本落在已核实的安全通告受影响区间，且有可行修复版本；或权威来源显示该包或该主版本线已弃用，并有可迁移目标；或落后**一个以上**大版本，并且能说明**明确收益**和**迁移成本**。三者任一成立，且建议动作在当前约束下可行。 |
| **可以升级** | 有更新，但不是必须马上做：例如落后一个大版本、常规 minor/patch、收益一般，或跨大版本尚需评估但值得排期。 |
| **暂不动** | 已是最新稳定版；或受 MSRV / SDK / runtime / 平台 / 许可证 / peer / BOM / constraints 等实际约束，升级目前不可行；或只有预发布版可追而项目未跟踪预发布线；或有通告但项目侧暂无可行修复路径（写明「上游阻塞 / 跟踪」）。 |
| **未核验（unchecked）** | 本轮未能从 registry 或权威来源得到可信结果：查询失败、超时、私有源未授权、清单无法解析等。 |

旧报告里的 `immediate` / `later` / `ok` / `unchecked` 分别对应「立即升级 / 可以升级 / 暂不动 / 未核验」。不要另造一套英文机器枚举当交付格式；写给代理和用户看时用上表中文分档。

## 立即升级的证据门槛

- **安全漏洞：** 必须引用官方公告、OSV、GHSA、RustSec 或同等权威通告，核对该通告的受影响区间是否覆盖**本仓库实际锁版本**，并写出修复版本。锁版本不在受影响区间、通告已撤回、或无法对应到具体坐标 → 不得按漏洞列为立即升级。没有可行修复版本时改为「暂不动（跟踪 / 上游阻塞）」，不要假装现在就能升级。
- **弃用：** 必须有维护者或发行方的权威说明（changelog、registry 弃用标记、官方公告）。不得仅凭「很久没发版」或社区传闻。
- **落后一个以上大版本且明显收益：** 「一个以上」指当前主版本与最新稳定主版本之间至少隔着一个主版本（例如仍停在 2 而最新稳定是 4）。必须同时写清收益（例如旧线停维、被其他已核实升级挡住、有明确的缺陷修复或项目需要的能力）和迁移成本（破坏性变更、API 重写、配套生态是否跟上）。**不能**只因为跨了多个大版本就自动列入立即升级；成本高、收益含糊的放到「可以升级」或「暂不动」。
- **不要盲追 latest：** 建议版本优先采用能消除已核实问题的**最小修复版本**，再给出在当前约束下的可行目标。latest stable 只是对照，不是默认目标。
- **不要把流行度或落后程度当成安全性。** 星标、下载量、落后几个版本，都不能代替通告。

## 什么算进主表

- 本轮范围内、该证据 SHA 下清单里的**直接依赖**（含该生态常规意义上的生产、开发、可选直接依赖，但要在表中区分用途）。
- 同时给出声明范围和锁版本；只有范围没有锁时，标明「无锁」，不要把范围写成已解析版本。
- 工作区 / monorepo 的每个清单都要归到对应包或路径，不要把根清单当成全部。
- 工具插件、构建依赖（如 Gradle 插件、Cargo `build-dependencies`、npm 的 packageManager / 引擎钉扎）若存在，单独成组，不要和运行时直接依赖混列。
- 版本目录、BOM、platform、constraints 是约束来源，用来解释「为何不能升」或「实际解析可能被谁钉住」，它们本身通常不是一行「包」。

## 什么要分开或排除

- **间接依赖：** 默认不进主表。只有当已核实的通告覆盖其锁版本、或用户明确要求时，才单独列出，并标明「间接」。不要把间接依赖的最新版写成直接依赖该升的目标，除非也能说明是谁把它引进来的、以及直接依赖侧的可行动作。
- **git / path / vendor / 文件协议、工作区内部包：** 无公开 registry 可查，单独成组；不要伪造 latest。能核对其引用提交或本地路径即可。
- **未在本轮清单中出现的生态：** 不要假装检查过。在「未覆盖」里写明。
- **预发布、yanked / retracted、许可证变更：** 最新稳定版不包括预发布，除非项目已经跟预发布线。锁版本已被 yanked 或 retract，要在证据里写明，并按是否有安全或停用依据来分档，而不是只标一个新数字。许可证变得无法接受时，当作约束或风险写清来源，不要用猜测代替文本。

## 覆盖与结论边界

按本轮范围和当前环境里实际能用的只读手段合理覆盖。仓库里实际出现过的生态都应尽力核对（常见如 npm / pip / Gradle / Cargo / Go / SwiftPM / ohpm，以及确实存在的其它清单，如 Maven、Pub、NuGet、Bundler、Composer、GitHub Actions 钉扎、容器基础镜像、工具链包装器）。某种生态完全没出现，就不要写进已覆盖。某种出现了但只核对了部分清单，必须在未覆盖里写清缺口。

结论限定为「在所述范围和方法内的核对结果」，不能声称全覆盖或「没有漏洞」——只能说已查来源里有或没有覆盖该锁版本的通告。
