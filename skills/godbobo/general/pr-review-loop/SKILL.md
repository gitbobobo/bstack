---
name: pr-review-loop
description: 在开 PR 前或收敛 PR 审查结论时使用。
---

请求复审后持续跟进至收敛。处理完一轮后保持对最新审查意见与检查状态的监听；一轮返回不代表任务已完成。

## 开 PR 之前

模版里的「创建 PR 前完成」就是本轮的交付门槛，PR 建完再回头读已经晚了一轮：缺项会先被审查者当意见提出来。所以创建 PR 之前先定模版：

1. 找仓库自己的模版：`.github/PULL_REQUEST_TEMPLATE.md`（含全小写与 `.github/PULL_REQUEST_TEMPLATE/` 目录）、`docs/` 下的模版，以及 `CONTRIBUTING.md` 里指定的模版。找到就整份用它、按它的结构填满，与本节规则冲突时以仓库为准；HTML 注释只当填写说明，正文不带注释。
2. 仓库没有模版时用 [references/pr-template.md](references/pr-template.md)：占位项换成仓库的真实入口（检查命令、启动方式、分层名称），无关小节删掉，不留空表格。
3. 描述写满「创建 PR 前完成」再创建：GitHub 用 `gh pr create --body-file '<文件>'`，Forgejo 用 `fj pr create`（正文同样按模版填），其他宿主按仓库自己的入口（REST 等）提交同一份正文。

## 跟进入口

1. 先读取当前 PR 的最新评论、审查结果和最新 HEAD 的检查状态，恢复工作树外的跨轮账本。快照与每一轮都核对最新 headRefOid，旧提交上的通过不能代替最新提交的检查与审查。读评论/意见列表记得带 `--paginate`——不带只回最旧 30 条，评论多的 PR 新意见永远不可见（Forgejo 用 `fj pr view <PR> comments` 与 `fj pr review <PR> list -c`，REST 按 `?limit=50&page=` 翻页）。bot 常在同一条评论里原地改写结论：快照按 `updated_at` 判新，凡是 `updated_at` 晚于账本上次快照的评论都算本轮输入。
2. 等齐本轮意见：本轮请求的和推送自动触发的审查者（上轮已超时的不算），都在最新 HEAD 上给出结论（或按第 6 步放弃等待）后，才开始归桶和修改；只到了一部分就继续监听，不边到边改。
3. 按「收敛规则」归桶 → 更新跨轮账本 → 判断是否触发方向审计。触发时先请方向顾问给出定性、按「方向取舍」定收敛路径，再恢复修复；只有产品决策按「暂停」交回用户。
4. 按确定的路径修复 → 核验或补跑相关检查 → 在已有提交/推送授权范围内提交推送 → 回复。每次请求复审或继续等待自动复审前，必须把本轮处置及升级判断写回账本，向用户简短说明各子系统的连续轮数、顾问定性（触发过审计时）和下一步，再按「审查者现状」重新触发本轮未通过的审查者。需要额外授权时先完成可审阅的修复，再交回用户。

   推送含可见 UI 改动的提交前：先重拍受影响界面、上传、按「回复」的宿主命令更新 PR 描述中的截图链接，再推送。push 时自动触发的审查者读的是当时的描述——先推后改，它按旧图审，会对已修问题再开一轮。上传前先打开图片，确认不是过渡帧或旧布局。

   本轮零 Act on、没有推送时，不会有自动复审来接你：推送是复审唯一的自动触发源，「等下轮」等的东西不会来。回复完全部意见就按「结束（静默）」自检——账本无 `待回报`、最新 HEAD 上每个审查请求都有结论、CI 通过——满足就走结束清单，汇报写明「已静默，等收尾指令」；还有审查者没出结论才按「审查者现状」补触发。
5. 本轮处理完后登记监听，并以此结束本轮：完成标准是监听登记调用已返回成功（T3 下 PR 已关联、`watch_pull_request` 成功，兜底定时任务存在），汇报末尾写明监听状态。新事件到达即回到第 1 步做快照。
6. 审查者超过「审查者现状」里的等待上限仍无结果时，按其下的「等待上限只花一次」处理。

结束跟进、因产品决策暂停、用户停止或交回用户前，撤掉仍在运行的监听。

## 审查者现状

当前接入的审查者与触发方式，名单变化时更新这里：

| 审查者 | 触发 | 等待上限 |
| --- | --- | --- |
| Codex | 每轮发一条顶层评论 `@codex review`；推送不会触发它 | 触发后 30 分钟 |
| fast-ship-bot | PR 开启、推送自动触发；也可发顶层评论 `@fast-ship-bot` | 推送或评论后 30 分钟 |

**等待上限只花一次。**某审查者超过等待上限仍无结果，本轮跳过它，结束时说明，并把超时记进账本；此后各轮不再为它等待，到齐判定不含它——云端审查者不一定一直在线，一轮缺席说明它当下不在，同一个上限不该每轮重付。手动触发的审查者照常发请求，只是不为它等待；它之后自己出了结论就按「审查意见按身份归属」正常回收，并恢复为正常等待。

推送触发的审查者超时后，本轮结束前重新触发一次：有重跑入口（API、评论命令）就用它；没有就推一个空提交 `git commit --allow-empty -m "chore: 重新触发审查（第 N 轮超时）"`。每次超时只重新触发一次，账本记一笔。

## 收敛规则

**审查意见按身份归属。**审查者各用自己的身份发言：审查者账号下的顶层评论与行内评论就是本轮意见，自己账号下的是本线程的回复，不进意见列表。作者分不出来时（同一账号被别的 agent 借用）才看 `<!-- pr-review-loop:reply -->` 标记：带标记是自己发的，不带的算新意见（见「回复」）。

处理本轮新意见之前，先把它们归并分桶，再按桶回复：

| 桶 | 含义 | 回复动作 |
| --- | --- | --- |
| Act on | 影响正确性、安全或可维护性的真实问题 | 先判断方向审计 → 按确定的路径修复、核验和回复 → 更新账本后重新请求这个审查者 |
| Consider | 说得对，但属于本 PR 需求目标之外的另一件事 | 回复「有道理，本 PR 不做，理由 X」，**不**重新请求 |
| Noted | 技术上成立但不可行动（依赖上下文、过早优化） | 简短确认，不改 |
| Dismissed | 错的、吹毛求疵的、缺上下文的 | 回复驳回理由并给依据 |

**云端 bot 的一致性要降权。**多个审查者独立提出同一件事通常是高信号，但前提是它们看了同一份输入。PR 上的云端 bot 输入并不相同——有的读了 PR 描述，有的只看 diff——所以「两个 bot 都提了 X」的置信度低于同输入的多模型审查。记录每条意见是谁提的，但不要让提的条数直接决定它进哪个桶。

**跨轮账本。**复审是多轮的，账本必须跨轮累积。写成一个 TSV，放在工作树之外（仓库约定不允许把临时文件留在工作树里），列为：`轮次 / 受审 HEAD / 子系统 / 审查者 / 意见摘要 / 桶 / 理由 / 回复链接 / 本轮状态`。`本轮状态` 用 `待回报` 标记已发出、结论还没回来的审查请求；这一行还在，收敛与合并都不成立。每轮快照与最新评论对账，记录各子系统连续出现 Act on 的轮数，以及方向审计结论或未触发理由。账本缺失或停在旧轮次时，先从 PR 历史补齐，再继续修复或复审。

**轮次按受审提交计。**同一 HEAD 上多个审查者的意见合为一轮；通知重放、已修复的旧意见和同一意见的重复报告不另计轮次。旧提交的迟到意见先核对当前 HEAD 是否仍成立。重启会话、rebase 或补发复审请求都沿用账本中的连续轮数。每次推送都作废上一轮的收敛结论，另起一轮由这次推送触发的审查——收尾期间推的提交同样算。

**不追目标分支。**审查只回答本 PR 的改动是否成立；与目标分支的整合留到用户收尾时一次完成。跟进与等待收尾期间，提交只为处理审查意见；目标分支前进、GitHub 显示冲突或被冲突事件唤醒都只记录，留给收尾。例外：本 PR 必须用到目标分支上的新改动才能通过审查或验证时，提前整合并在账本写明理由。

**Dismissed 跨轮复用。**一条意见在上一轮已被 Dismissed，下一轮另一个审查者又提同样的，引用上一轮的驳回理由和那条回复的链接，不要重新辩论一遍。

**三轮未收敛先做方向审计。**同一子系统连续 3 轮仍有有效的 Act on 意见，无论 bot 标为 P0、P1、P2 或未标级别，收到第三轮意见后先停下逐条修补与复审循环，派一位**方向顾问**独立审整份 diff——编排环境下用 `$t3-orchestrator` 的 `--task design` 选人，没有编排时用 harness 自带的只读子代理，选与主代理不同模型家族的一位。审查三问：实现方向是否成立、反复出现的问题是否有共同根因、剩余修复能否沿当前方向收敛。三轮 Act on 本身就是「方向归我自己拍板」不成立的证据，这个判断不归你单独做；顾问定性回来并写进账本，审计才算完成，在那之前不动手修。定性只有三种：

- **有限清单**：意见指向不同的具体缺陷，每轮新意见在减少。沿当前方向继续修。
- **开放反例**：意见是同一机制上不断冒出的新反例，比如用词法/正则判断语义、枚举无穷的输入形态、拿时序余量对抗竞态。修完一种写法审查者总能再找出一种，当前方向本身不会收敛。二选一：换掉生反例的模型（如换成 AST/类型系统、信号驱动、单一事实源），或把覆盖范围收窄到仓库里真实出现的情形。选定后把覆盖范围写进 PR 描述和代码注释，此后落在范围外的同类意见归入 Consider，回复时引用这段范围说明。
- **范围扩张**：意见主要落在 PR 为修前几轮意见而扩张出去的部分。对照原始需求圈定必须交付的范围，范围外已做的部分拆成独立 PR 或独立问题，本 PR 只收敛圈定范围。

定性为开放反例或范围扩张时，**审计的完成标准是路径已经落地**，而不是交出一份建议：

1. 账本里记下顾问定性与你的判断（不一致时写清取舍依据）；
2. PR 描述里已经有「交付范围」一节，写明本 PR 管什么、不管什么（按「回复」表的改描述命令已执行）；
3. 范围外的已有改动已经处理：按 `git diff <base>...HEAD --stat` 以文件为单位归类，不逐个提交甄别；范围外文件拆到新分支/新 PR，或建跟进问题并在 PR 描述「不管什么」里列出这些文件；换修法的改动已经提交；
4. 账本里记下「收敛路径」：交付范围、范围外意见的固定回复文案。

四项都做完才恢复审查循环。不涉及产品决策的拆分与收窄由你自己做，只把结果告知用户。此后每轮第 3 步归桶前先读账本里的收敛路径：落在范围外的意见（即使标 P1/P2）一律归 Consider，用固定文案回复并引用 PR 描述里的范围说明；只有范围内的意见进 Act on。确实是范围内的正确性问题（如 panic、数据损坏、凭据泄露）照常修。

同一子系统在上次审计后又连续 3 轮有 Act on，下一次审计先检查上次的定性是否仍成立：定为有限清单却没有减少，按开放反例重判；范围已圈定却仍在修范围外的意见，说明收敛路径没有被执行，先补执行。审计定性（与你的判断不一致时按「方向取舍」裁决）与选定路径写入账本后，才恢复修复。只有完成方向审计并确定路径，或该子系统一轮审查结束且没有有效 Act on 意见，才重置连续轮数。

## 方向取舍

定性之外的路径、修在本 PR 还是另立需求、补不补回归与夹具，由你自己定，默认**根治**：选长期更干净正确的方案——在本 PR 内修掉共同根因、换掉反复生边界的模型、补上能变异验证的回归。PR 已经很大、审查轮次已经很多，都不是延后的理由；「另立需求」「记档不修」只留给本 PR 需求目标之外的事。顾问定性你不认同、或修法互相冲突时，按根治取向自选，把取舍和依据写进账本后直接继续。

## 回复

回复正文先写进 UTF-8 无 BOM 的临时文件，不要把中文内联在命令里。宿主按 PR URL 判断：github.com 用 `gh`；其他实例（Forgejo/Gitea）用本机 `fj`，缺命令或未登录时退回同名 REST 端点（`/api/v1/...`，凭据取 `FORGEJO_TOKEN`、`~/.agents/env/forgejo.sh` 或本机 git credential helper）。

| 动作 | GitHub | Forgejo |
| --- | --- | --- |
| 回复行内意见 | `gh api repos/<repo>/pulls/<n>/comments -X POST -F in_reply_to=<线程第一条评论的 id> -f body="$(cat '<文件>'; printf '\n\n<!-- pr-review-loop:reply -->')"` | 没有 `in_reply_to`：在对话区发顶层评论，开头引用原意见并附它的 `html_url`（`fj pr comment <PR> --body-file '<文件>'`）。必须落回同一段 diff 时用 `POST /api/v1/repos/<owner>/<repo>/pulls/<n>/reviews/<review id>/comments`，body 带 `path`、目标行的 `new_position`（或 `old_position`）和正文，review id 先 `GET /api/v1/repos/<owner>/<repo>/pulls/<n>/reviews` 取 |
| 顶层评论、审查总结、bot 结论 | `gh api repos/<repo>/issues/<n>/comments -X POST -f body="$(cat '<文件>'; printf '\n\n<!-- pr-review-loop:reply -->')"`，正文开头引用被回复的意见或附上它的链接 | `fj pr comment <PR> --body-file '<文件>'`（标记写进文件末尾）；或 `POST /api/v1/repos/<owner>/<repo>/issues/<n>/comments` |
| 改 PR 描述（交付范围、截图链接） | `gh pr edit <n> --body-file '<文件>'` | `fj pr edit body "$(cat '<文件>')"`；或 `PATCH /api/v1/repos/<owner>/<repo>/pulls/<n>` |
| 读评论与检查状态 | `gh pr view`、`gh pr checks`、`gh api … --paginate` | `fj pr view <PR> comments`、`fj pr review <PR> list -c`、`fj pr status <PR>` |

**自己发的每条评论末尾都要带 `<!-- pr-review-loop:reply -->` 标记**（HTML 注释，两个宿主渲染后都不可见）——回复、处置总结、更正都一样。下一轮按作者就能排除自己的评论，标记是同一账号被别的 agent 借用时的唯一判据，照发不要省。Forgejo 走 `--body-file` 时把标记写进文件末尾；GitHub 在 Windows 下 `$(cat …)` 不可用时也写进文件，再用 `-F body=@<文件>` 提交。

不要对任何评论执行 `PATCH` 或 `DELETE`，自己账号发的也不行——两边 API 有权限时都不会拦（Forgejo 的 `fj pr edit comment` 同样不用），改错了就会覆盖审查结论。回复发错了就再发一条更正，不要改原评论。修改 PR 描述不受这条限制，命令见上表。

## 暂停

只有需要产品决策的意见（用户可见行为、文案或交互语义要变，需求与项目文档都没给答案）才停下来问用户：先撤掉监听，汇总问题、可选路径及推荐项，收到选择后再恢复循环。技术方向、范围与修法的分歧按「方向取舍」处理。

## 结束（静默）

静默：最新提交上的每个审查请求都有结论（或已按上面的规则放弃等待并把那一行结掉），没有未处理的有效意见，CI 通过，账本没有 `待回报` 行。本轮修复还没推送就先推送再判静默——留在工作区等收尾，收尾那次推送就绕过了审查。静默只对那个提交成立。

1. 撤掉仍在运行的监听。
2. 勾选 PR 描述中「审查意见处理」的待办项（用「回复」表里的改描述命令）。
3. 向用户简短汇报：共几轮；修了什么；哪些意见没改、理由是什么；哪个审查者无响应。
4. 不要合并 PR，等用户的收尾指令；收尾期间的推送重新等静默（见 `$pr-finish` 第 4 步）。
