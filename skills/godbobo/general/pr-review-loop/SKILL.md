按「开放审查 → 定向修复 → 冻结验收」推进到可合并标准：重大问题已解决，剩余低风险问题已有明确处置。合并动作另按已有授权执行。审查检验交付契约，最终源码上的行为与检查证据决定完成；外部审查回报是必要门禁之一。

## 开 PR 之前

模版里的「创建 PR 前完成」就是本轮的交付门槛，PR 建完再回头读已经晚了一轮：缺项会先被审查者当意见提出来。所以创建 PR 之前先定模版：

1. 找仓库自己的模版：`.github/PULL_REQUEST_TEMPLATE.md`（含全小写与 `.github/PULL_REQUEST_TEMPLATE/` 目录）、`docs/` 下的模版，以及 `CONTRIBUTING.md` 里指定的模版。找到就整份用它、按它的结构填满，与本节规则冲突时以仓库为准；HTML 注释只当填写说明，正文不带注释。
2. 仓库没有模版时用 [references/pr-template.md](references/pr-template.md)：占位项换成仓库的真实入口（检查命令、启动方式、分层名称），无关小节删掉，不留空表格。
3. 从需求和仓库约定提取交付契约：必须交付的行为、必须保持的不变量、范围边界，以及对应的正常、失败、取消与并发路径验证（按实际风险取舍）。已有 PR 先从原始需求恢复这份契约。契约放在 PR 描述中，账本引用它；新增意见须说明违反哪条契约或引入了什么回归。
4. 描述写满「创建 PR 前完成」再创建：GitHub 用 `gh pr create --body-file '<文件>'`，Forgejo 用 `fj pr create`（正文同样按模版填），其他宿主按仓库自己的入口（REST 等）提交同一份正文。

## 跟进入口

1. 先读取当前 PR 的最新评论、审查结果和最新 HEAD 的检查状态，恢复工作树外的跨轮账本。快照与每一轮都核对最新 headRefOid，旧提交上的通过不能代替最新提交的检查与审查。读评论/意见列表记得带 `--paginate`——不带只回最旧 30 条，评论多的 PR 新意见永远不可见（Forgejo 用 `fj pr view <PR> comments` 与 `fj pr review <PR> list -c`，REST 按 `?limit=50&page=` 翻页）。bot 常在同一条评论里原地改写结论：快照按 `updated_at` 判新，凡是 `updated_at` 晚于账本上次快照的评论都算本轮输入。
2. 等齐本轮意见：本轮请求的和推送自动触发的审查者（上轮已超时的不算），都在最新 HEAD 上给出结论（或按第 6 步放弃等待）后，才开始归桶和修改；只到了一部分就继续监听，不边到边改。
3. 按「收敛规则」归桶，核对当前阶段和契约 → 更新跨轮账本 → 判断是否触发「方向审计」。触发时先完成审计与路径落地，再恢复修复；只有产品决策按「暂停」交回用户。
4. 将本轮有效意见按共同根因批量修复，检查同构入口和相邻失败路径 → 由唯一最终验证负责人核对受影响模块、调用方及既有测试的覆盖，补跑缺口 → 在已有提交/推送授权范围内一次推送本轮提交 → 回复。格式与定向检查在推送前完成，避免修正提交连续触发重叠审查。每次请求复审或继续等待自动复审前，必须把本轮处置及升级判断写回账本，向用户简短说明当前阶段、有效修复轮数、未结清单项和下一步，再按「审查者现状」重新触发本轮未通过的审查者。需要额外授权时先完成可审阅的修复，再交回用户。

   推送含可见 UI 改动的提交前：先重拍受影响界面、上传、按「回复」的宿主命令更新 PR 描述中的截图链接，再推送。push 时自动触发的审查者读的是当时的描述——先推后改，它按旧图审，会对已修问题再开一轮。上传前先打开图片，确认不是过渡帧或旧布局。

   本轮零 Act on、没有推送时，不会有自动复审来接你：处理当前已发出的请求即可，无需另起一轮。回复完全部意见就按「结束（静默）」自检——账本无 `待回报`、最新 HEAD 上每个审查请求都有结论、CI 通过——满足就走结束清单，已有收尾授权就继续 `$pr-finish`，否则汇报「已静默，待合并」；还有审查者没出结论才按「审查者现状」补触发。
5. 本轮处理完后登记监听，并以此结束本轮：完成标准是监听登记调用已返回成功（T3 下 PR 已关联、`watch_pull_request` 成功，兜底定时任务存在），汇报末尾写明监听状态。新事件到达即回到第 1 步做快照。
6. 审查者超过「审查者现状」里的等待上限仍无结果时，按其下的「等待上限只花一次」处理。

结束跟进、因产品决策暂停、用户停止或交回用户前，撤掉仍在运行的监听。

## 审查者现状

当前接入的审查者与触发方式，名单变化时更新这里：

| 审查者 | 触发 | 等待上限 |
| --- | --- | --- |
| Codex | 每轮发一条顶层评论 `@codex review`；推送不会触发它 | 触发后 30 分钟 |
| fast-ship-bot | PR 开启、推送自动触发；也可发顶层评论 `@fast-ship-bot` | 推送或评论后 30 分钟 |

**等待上限只花一次。**某审查者超过等待上限仍无结果，本轮跳过它，结束时说明，并把超时记进账本；此后各轮不再为它等待，到齐判定不含它——云端审查者不一定一直在线，一轮缺席说明它当下不在，同一个上限不该每轮重付。后续需要它复核时可发请求，只是不为它等待；它之后自己出了结论就按「审查意见按身份归属」正常回收，并恢复为正常等待。

审查超时可用 API 或评论命令重试一次，并记账；没有重跑入口时按超时规则结掉请求。保持源码 HEAD 稳定，不用空提交催审。宿主元数据异常先核对远端引用与 API 的差异，作为外部阻塞处理。

## 收敛规则

**审查意见按身份归属。**审查者各用自己的身份发言：审查者账号下的顶层评论与行内评论就是本轮意见，自己账号下的是本线程的回复，不进意见列表。作者分不出来时（同一账号被别的 agent 借用）才看 `<!-- pr-review-loop:reply -->` 标记：带标记是自己发的，不带的算新意见（见「回复」）。

处理本轮新意见之前，先把它们归并分桶，再按桶回复：

| 桶 | 含义 | 回复动作 |
| --- | --- | --- |
| Act on | 按「可合并标准」判断必须在交付前解决的阻断问题 | 先判断方向审计 → 按当前阶段修复、核验和回复 → 更新账本后请求增量复核 |
| Consider | 有效但不阻断：低风险缺陷、可选增强或范围外问题 | 记录影响、接受依据和后续去向，回复后不为此单独请求复审 |
| Noted | 技术上成立但不可行动（依赖上下文、过早优化） | 简短确认，不改 |
| Dismissed | 错的、吹毛求疵的、缺上下文的 | 回复驳回理由并给依据 |

### 可合并标准

主代理按影响、触发条件、波及范围和恢复成本自主分级，依据复现或可核验因果链裁决；bot 的 P0/P1/P2/Note 只是线索。目标是主要需求可靠交付、重大风险受控，允许留下已说明的低风险问题。

- **必须解决**：数据丢失或损坏、凭据泄露/越权、崩溃/死锁/严重卡顿、核心流程不可用或显著错误、公共契约破坏，及影响或波及范围较大的回归。低概率本身不能豁免高后果问题；仓库强制门禁照常满足。
- **可自主接受**：影响轻微、触发边界明确、容易恢复，且不破坏主要需求或安全与数据完整性的问题，如次要展示瑕疵、非关键路径的小体验问题、局部可维护性欠缺。即使由本 PR 引入也可归 Consider；账本记录影响、边界、接受理由及后续去向，汇报时说明，无需逐项请用户批准。
- **证据不足**：先做最小复现或定向核验，确认实际影响；潜在高后果风险在排除前保持 Act on。真实问题若明显超出本 PR，记录跟进；拆分不能掩盖本 PR 引入的重大风险。

修复投入按收益与新增风险取舍：开放审查时可随同根修复顺手解决低风险项；冻结后默认保留并记录，避免小修引出新的行为变化和复审。所有意见须完成分级与处置，完成标准不要求所有有效意见都改代码。

**云端 bot 的一致性要降权。**多个审查者独立提出同一件事通常是高信号，但前提是它们看了同一份输入。PR 上的云端 bot 输入并不相同——有的读了 PR 描述，有的只看 diff——所以「两个 bot 都提了 X」的置信度低于同输入的多模型审查。记录每条意见是谁提的，但不要让提的条数直接决定它进哪个桶。

**跨轮账本。**复审是多轮的，账本必须跨轮累积。写成一个 TSV，放在工作树之外（仓库约定不允许把临时文件留在工作树里），列为：`轮次 / 受审 HEAD / 子系统 / 审查者 / 意见摘要 / 桶 / 理由 / 回复链接 / 本轮状态`。`本轮状态` 用 `待回报` 标记已发出、结论还没回来的审查请求；这一行还在，收敛与合并都不成立。每轮快照与最新评论对账，并记录阶段、各子系统有效修复轮数、审计清单及验收检查点进展。账本缺失或停在旧轮次时，先从 PR 历史补齐，再继续修复或复审。

**轮次按受审提交计。**同一 HEAD 上多个审查者的意见合为一轮；通知重放、已修复的旧意见和同一意见的重复报告不另计轮次。旧提交的迟到意见先核对当前 HEAD 是否仍成立。重启会话、rebase 或补发复审请求都沿用账本中的连续轮数。每次推送都作废上一轮的收敛结论，收尾期间同样如此。另记「有效修复轮」用于审计触发：等齐意见后批量处理有效 Act on 算一次；格式修正、空提交、旧 HEAD 迟到或被替代的审查只记请求状态，不增加有效修复轮数，也不计入有效验收轮。

**不追目标分支。**审查只回答本 PR 的改动是否成立；与目标分支的整合留到用户收尾时一次完成。跟进与等待收尾期间，提交只为处理审查意见；目标分支前进、GitHub 显示冲突或被冲突事件唤醒都只记录，留给收尾。例外：本 PR 必须用到目标分支上的新改动才能通过审查或验证时，提前整合并在账本写明理由。

**Dismissed 跨轮复用。**一条意见在上一轮已被 Dismissed，下一轮另一个审查者又提同样的，引用上一轮的驳回理由和那条回复的链接，不要重新辩论一遍。

## 方向审计

开放审查阶段，同一子系统连续 3 个有效修复轮仍有 Act on，或同一阻断问题修两轮仍不收敛、修法出现反向修改时，先停止逐条修补，派一位不同模型家族的只读方向顾问。编排环境用 `$t3-orchestrator` 的 `--task design` 选人，否则用 harness 子代理。传递交付契约、整份 diff、历轮意见及回应、原始验证证据；复审额外传上次预测与实际结果。

顾问回答方向是否成立、问题是否同根、剩余工作能否枚举，并给出一种定性：

- **有限清单**：方向成立，剩余缺陷可枚举。逐项编号，给出因果证据、修复边界与验收条件；说明为何其他同构入口已覆盖。
- **开放反例**：同一机制不断产生新反例。替换生反例的机制，或在满足原始需求的前提下收窄支持范围。
- **范围扩张**：新增问题主要来自修复扩出去的行为。对照原始需求拆除或另交付范围外部分。

三种定性都以路径落地为完成标准：PR 描述更新交付契约与范围；账本记录定性、编号清单、验收证据要求和取舍；范围外已有改动按行为与依赖拆分（同文件可同时含范围内外代码），或说明其保留理由及跟进条目；换机制时改动已实现并验证。本 PR 引入的重大回归必须解决；低风险遗留统一按「可合并标准」记录接受。

技术取舍由主代理根据因果证据与交付契约裁决，优先消除共同根因。顾问意见相反时先明确双方依赖的前提，用代码或实验核对；按证据选择并写回账本。审查级别、最新一条建议或其他端的写法都不能单独决定修法。

## 定向修复与冻结验收

审计路径落地后进入**定向修复**：按编号清单批量完成修复、同构入口检查与验证。复核只覆盖清单、改动范围及相关回归，传递原始意图、历轮回应和未解决异议。有限清单之外又出现同根阻断缺陷，或修复引入阻断回归、反向修改时，立即复审上次预测，按开放反例或范围扩张重新判断；审计本身不清零历史。只有一个完整有效轮无 Act on 才结束连续计数。

清单阻断项已修复验证、低风险项已按「可合并标准」记录接受后进入**冻结验收**，在账本记录冻结 HEAD，每 2 个有效增量验收轮核对一次收敛进展。保持交付行为固定，审查只确认修复及相关回归。自动全量审查仍按以下门槛接收意见：

- 意见按「可合并标准」分级，只有阻断项继续修复；因本 PR 新增调用路径而暴露的缺陷也按实际影响判断。
- 基线既有问题、可选增强与 Note 默认记录或另立问题；Note 若满足上述门槛，按真实缺陷处理。级别不代替证据。
- 证据对应当前 HEAD，必要正常与失败路径已验证，审查请求均结清且 CI 通过，立即按「结束（静默）」交付；无需补一轮找错。

每个当前 HEAD 等齐意见并完成增量判定算一个有效验收轮；有修复则批量验证、推送后验收新 HEAD。旧 HEAD 的绿灯不能放行新 HEAD。两轮是自主调整方法的检查点，任务持续推进到可合并：

- 清单在减少、剩余修复边界明确：主代理继续批量修复与增量验收，记录剩余项和证据；无需为续跑单独派顾问。
- 同根阻断反例、反向修复或修复范围持续扩张：立即按「方向审计」复核，主代理选定并实施根因修正；满足原始需求的前提下可移除可选增强、拆分独立改动或换机制。顾问返回多个方案时主代理根据证据选定，继续实现和验证。
- 最新 HEAD 只差在途审查或检查：登记监听，收到结果后继续；等待与旧 HEAD 迟到结果不构成重设计理由。

完成标准是主要交付目标满足、阻断问题已解决、低风险遗留已记录、最新 HEAD 门禁通过；轮数、顾问回报和方案说明都是中间状态。保持同一方案的完整历史，不以检查点为由结束任务、交回技术选项或降低合并门禁。只有缺少必要产品决策或授权时才按「暂停」处理。

收尾整合或新推送保留阶段、清单和验收历史，核验改变范围与最新 HEAD；不会重置成开放审查。等待结果按「跟进入口」登记监听并结束本轮。

## 回复

回复意见、更新 PR 描述或读取宿主评论与检查时，读取 [references/replies.md](references/replies.md)，使用对应宿主的文件提交方式和回复标记。

## 暂停

只有需要产品决策的意见（用户可见行为、文案或交互语义要变，需求与项目文档都没给答案）才停下来问用户：先撤掉监听，汇总问题、可选路径及推荐项，收到选择后再恢复循环。技术方向、范围与修法的分歧按「方向审计」的证据裁决规则处理。

## 结束（静默）

静默：最新提交上的每个审查请求都有结论（或已按上面的规则放弃等待并把那一行结掉），交付契约与审计清单在最终源码上都有必要行为和检查证据，阻断问题已解决，低风险遗留已记录接受，没有未处置意见，CI 通过，账本没有 `待回报` 行。本轮修复还没推送就先推送再判静默——留在工作区等收尾，收尾那次推送就绕过了审查。静默只对那个提交成立。

1. 撤掉仍在运行的监听。
2. 勾选 PR 描述中「审查意见处理」的待办项（接口见「回复」引用）。
3. 向用户简短汇报：共几轮；修了什么；哪些意见没改、理由是什么；哪个审查者无响应。
4. 按已有授权继续：用户已要求合并、收尾或端到端交付到主分支时，直接执行 `$pr-finish` 到 MERGED，无需再次确认；明确只审查或要求停在待合并时，交付可合并结果。收尾期间的推送重新等静默（见 `$pr-finish` 第 4 步）。
