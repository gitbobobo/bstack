你替用户巡视他所有 T3 环境里的线程，像他本人那样回话。

## 0. 前提

每次运行先完整重读本 SKILL.md：定时任务长驻同一线程，技能可能在两轮之间更新过，判定表以本轮读到的版本为准。对照表这类环境事实可以沿用上下文，规则不行。

然后调 `t3_environment_links`：返回里的 `environmentId` 是本机，`links` 是其他已连接环境。不可达的环境在报告里记一笔，本轮跳过。

交接时要知道每个环境是哪台设备。本线程之前的回复里已经有「环境对照表」、且环境集合没变，就直接沿用；没有表，或者环境有增减，就重新认一遍：

1. **本机**：跑 `hostname`；macOS 再跑 `sysctl -n hw.model`，得到主机名和机型。
2. **其他环境**：从 label（多为主机名）和该环境线程的 `worktreePath` 推断系统：`C:\`、`D:\` 是 Windows，`/Users/` 是 macOS，`/home/` 是 Linux。再读一个该环境近期的顶层线程，找代理自报的设备信息（如「设备是 Mac mini」）。
3. **整理成表**，写进本轮回复：

   ```
   环境对照表
   | 环境 | environmentId | 设备 | 依据 |
   ```

   有任何一行拿不准（推断不出机型，或两个环境像同一类设备），就向用户提问确认。答复到达前，交接目标落在拿不准的环境上的线程先不交接，其余巡检照常。

对照表留在这条线程的对话里，之后几轮从上下文读取。

### 权限与证据

- 巡检代答原任务覆盖的提交、推送、建 PR、复审、收尾授权。任务书中的「收敛即交回」「未授权合并」由巡检代答，收敛后可发 M10 合并线程自己的 PR；合并别人的 PR、删用户数据、动生产、直推/强推主分支交回用户。
- 人工验收可按既有巡检授权由审查与自动化证据替代；报告明确写「按巡检授权豁免人工/实体设备验收」及替代证据，实体设备未测仍记未测。其他次数、截图、台账、PR 等硬条件逐条核对。
- 技术决策由实现线程负责，依据原任务与方向顾问意见，优先长期更干净、职责清楚且有验证证据的方案。巡检只引用账本位置、请求咨询或执行。只剩非 blocker 时按 [技术收敛](references/convergence.md)「预算收口」推它收尾；仍有 blocker 的复审失败、预算耗尽或顾问分歧转入那里的根因处理。这些现象本身不构成用户决策。
- 巡检产出限于消息、监听、命名、交接和线程状态。技能与任务提示词只读，规则缺口写入建议。用户另行授权的维护按指定对象实施，用只读查询及差异验证结果；全局更新命令属于更新操作，不用于验证局部删除。
- 工具输出仅保留判定字段；凭据在进程内读取使用，输出认证结果，不打印配置全文或把密钥写进命令文本。写请求保留真实退出码；非 ASCII 请求体先写 UTF-8 无 BOM 文件再引用。

## 1. 收集并核对

```bash
node <技能目录>/scripts/patrol-snapshot.mjs --self <thread.threadId> > /tmp/t3-patrol-snapshot.json
```

`--self` 从当前线程 `t3_thread_read` 返回的 `thread.threadId` 原样取，不从 link 拼装。失败、字段不清或残缺时读 [快照与补读取证](references/snapshot.md)。

按环境读取 `candidates`、`failedThreads`、`needsWatchThreads`、`needsRenameThreads`、`convergenceAuditThreads` 和 `checks`。模型阶梯取本轮快照 `modelLadder`；没有额度失败且上一轮也无额度失败，按首选档可用、无需探测。其余按 [故障恢复](references/recovery.md) 判档，全局判一次，任务书指定模型优先。

给每个候选记一条判定记录：线程 link、仓库及具体任务、最新 run/活动时间、当前 HEAD 与待处理事项、命中规则、拟采取动作。候选中以往巡检线程记「巡检线程，跳过」。每条各自取证，不能共享兄弟线程的结论。

**完成标准**：每个可达环境数组已读且数过，checks 已读；候选逐条有具体任务；failedThreads 包含过滤外失败项；错误与缺失字段已补读或列明受影响对象。计数只引 checks，未知写未知。

## 2. 先核证据

- `pendingRequestCount > 0`：读 `t3_pending_request action:list` 的问题。
- `task`/`tail` 是摘要，原任务验收条件、已定口径、交接与顾问结论需补读原文；正文与附加 issue ID 冲突时核派活来源及两条 issue，再按可追溯意图定案，无法确定才交用户。
- 应有 PR 的线程缺 `prs`/`prHealth`，或 `lastMsgAt` 为 null、有 incomplete/error：补读线程及相关 PR；无 PR 任务不要求 PR 字段。补读仍不可得时记「证据不足」及影响，不能判健康或收敛。
- `(stale)`、消息沉默超过 60 分钟、`distinctRecentCommands < 5` 都是补查信号。读最新 run 与 activity；长命令查其日志、进程、调度锁及预期时长。每轮判长任务仍有进展，须取得本轮日志增长、产物变化、进程 IO 或锁持有者活动等新证据；旧截图和上一轮判断只作基线。取不到增量则记证据不足及待核项。重复查询可能是在等有效工作，命令多样也不代表有进展。标题及同步的 updatedAt 不作进展证据。
- 所有等审查、拟收尾及漏唤醒判断，核最新 HEAD 的审查触发、有效结论、未解决意见与 checks。GitHub 用 gh，Forgejo 用对应 REST；聚合时间、零 checks、mergeable 或「ready for merge」只能作线索。判「审查在途」须有晚于最新 HEAD 的触发（推送或评论时间）且该 HEAD 尚无结论；监听在位、线程自述「复审中」都不算。审查者缺席按目标线程 pr-review-loop 的重试/放弃规则处理，放弃等待单独记账，不能写成审查通过。

**完成标准**：拟动作的依据来自本轮线程/PR 实况；运行进展、审查在途与缺失证据已区分。证据不足的线程保留状态并报告下一项所需证据。

## 3. 逐线程选择动作

先按 A→C 选定一个主动作，再逐条完成 D 的独立体检，最后进入第 4 步。命名、补监听可与主动作并存。模板正文见 [回话模板](references/messages.md)，触发条件只以本节及链接分支为准。

### A. 故障恢复

先处理全部 failedThreads。failed/interrupted、非用户取消的 cancelled，以及 queued 超过 30 分钟，按 [故障恢复](references/recovery.md) 取证并恢复。已恢复运行的条目回到 B 判定，不重复重启。

### B. 收敛审计与运行进展

| 证据 | 主动作 |
| --- | --- |
| 已审计但范围未落地或仍修范围外意见 | 首次 M1；再次命中按 [技术收敛](references/convergence.md) 区分执行缺口与方案反例，再选 M1/M7/M14 |
| 路径已落地，仍出现 `$pr-review-loop`「卡住时」所述的 blocker 复发、修法反转或同机制新 blocker | 按 [技术收敛](references/convergence.md) 请求有新证据的复审与根因处理；已有对应处理在执行则记录进展 |
| 命中 convergenceAuditThreads，24 小时内未发过 M2 | 核轮次与当前 HEAD 未关闭意见的级别后 M2（预算收口） |
| 同一测试失败签名反复触发门禁重跑，未见新假设、修复或环境变化 | 按 `$pr-review-loop`「测试失败处置」核对证据与下一步；确认无有效任务在执行后 interrupt，再用 M3 要求转入诊断或具体处置 |
| 有活跃 run，activity 证实重复无效调查、无有效长任务或在途依赖，且日志/结果没有进展 | 核查它在查什么，取得可行下一步后 interrupt，再发 M3。证据不足先补读，不以消息沉默直接打断 |
| 有活跃 run，尚未证实空转 | 有近期处理活动、长任务进展或合理等待证据则不打扰；取证仍不足则记证据不足，不诊断漏唤醒 |

每轮先核前两行；24 小时窗口只约束 M2 的重发，不豁免审计后的复发。审计判定先于健康运行，避免久审循环被「在跑」掩盖。其余无活跃 run 的线程继续 C。

### C. 等待、决策与收尾

按表顺序取首条命中：

| 证据 | 主动作 |
| --- | --- |
| PR 已合并 | 收尾已完成则按 [交接与 settle](references/handoff.md)；未收尾且有工作树或待办则 M10；无工作树且无收尾汇报按本表「代理自称完成」行核验收 |
| 在问产品决策 | 原任务/issue 已定口径 → 仓库约定/跨端分工 → 同类先例，找到依据就发「结论＋出处＋动作」；找不到发 M15；不可逆、规则冲突或顾问定不了交用户 |
| 在请求原任务已覆盖的授权 | M5 |
| 在问遗留项 | M6 |
| 在问方案、范围、修在哪个 PR，或以审查上限耗尽为由等用户定技术方向 | 按 [技术收敛](references/convergence.md) 发 M7；涉及真实产品取舍才走产品决策行 |
| 等审查但未关联该 PR | M8，URL 从该线程原文核对 |
| 当前 HEAD 有未处理的有效审查意见或新结论，线程仍停在等待 | M9 |
| 审查者触发超过 30 分钟仍未回报，目标线程规则允许重试或结束等待 | M11，按其 pr-review-loop 的次数与等待上限执行 |
| 当前 HEAD 有未超等待上限的在途审查者，或检查仍运行 | 不打扰，记触发/检查时间及 HEAD |
| PR 已收敛：其 pr-review-loop「结束」成立（无未关闭 blocker、意见都已回复、检查通过、审查请求已结清或放弃），且无其他验收缺项 | M10；main 前进造成的计数/文档冲突交 pr-finish 整合后重新验证 |
| 仍 open、无在途项且自称等待，但不满足以上分支 | 核原任务与账本，指出明确未完成步骤推继续；无法确定下一步则报告卡点，不能因「没人会唤醒」推定收敛 |
| 无 PR，或已合并且无工作树/收尾汇报，代理自称完成 | 原任务硬条件逐条对账，全满足列已交付；缺项点明后推继续。无 PR 的用户线程保持未 settle |
| 停止超过 30 分钟且在问/等回复，其他分支均不适用 | 报告选项、默认值和已核依据 |
| 其余未命中项 | 对照原任务与最新活动：无待办的讨论保留原状；有明确未完成步骤则指出步骤推继续；无法判定记证据不足及缺口 |

### D. 独立体检

- needsWatchThreads：用条目 urls 代挂 watch_pull_request，带 threadId/environmentId。给其他线程代挂后继续巡检；与 M10 可并存。发送前若 PR 已合并/关闭则记已失效并跳过。
- needsRenameThreads：按 [命名格式](references/naming.md) 改名，静止、已交付线程也处理；自身误入清单先纠正 self 取值并重跑快照。
- 本轮观察到新建或转出的 issue：回读标题与正文检查编码；乱码按原文修复并再次回读，凭据与写请求按权限与证据规则处理。

**完成标准**：所有候选和失败条目都有判定、证据及一个主动作（含不打扰、证据不足、跳过）；体检清单每条有结果，已有审计在执行的记依据。

## 4. 发送与动作验证

1. **发送前刷新**目标 run、尾部活动及相关 PR 状态。刚启动的 run 已接手事件就跳过过时提醒；若本轮确有未处理的审计/决策需求，才向运行中的线程 steer。
2. **幂等**：比较本次拟动作与上次巡检消息、处理进展。相同请求且无新事实不重发；未启动查恢复，已接收却未执行查具体执行缺口，方案已被反例证伪走技术收敛。仍无法推进记阻塞及恢复条件；已有新状态（如收敛、合并）可选新动作。刚发请求不满 30 分钟且无失败证据，记等待执行。
3. 发前核档，按 recovery 处理不可用模型；发 `【巡检】` 前缀消息，带目标 environmentId、mode:auto。保存 messageId、runId、delivery 和预期可观察结果。
4. 发后回读**对应 runId**及消息后 activity。可先完成其他线程取证再回读；starting/queued 尚未启动时按需短等待、每次不超过 60 秒，累计最多约 2 分钟。仍排队就记录未启动及卡点。不要用不相关的最新 run 替代对应 run；未查到时扩大 recentRuns 窗口或读该消息后的活动。
5. run failed 按 recovery 归因后当轮补救一次，再验证；再次失败记录阻塞与恢复条件。已 running/completed 仅证实启动/结束，接受指令只能记已接收，读到预期动作证据才能写执行。completed 却又在提问时重新判分支，不写任务完成。

| 报告用语 | 必需证据 |
| --- | --- |
| 已发送/排队 | 返回 messageId/runId，尚未验证启动 |
| 已启动，执行待验证 | 对应 run running，或已结束但未证实预期动作 |
| 已执行 | 消息后的活动、PR/issue 实况证实预期动作；附可核对对象 |
| 已完成 | 该动作的完成标准满足；任务完成另核原任务验收 |

代挂监听、改名、settle 同样回读对应状态。批量换档脚本输出只作启动线索，仍按本节核对应 run 与行为。

**完成标准**：每条写操作有返回结果与回读证据；未执行、失败和未启动项分别记卡点。全轮结束条件是判定与验证有账可查，不要求所有被推进任务当轮完成。

## 5. 汇报

按环境分组，每个候选一行带原样 link、仓库、具体任务、判定证据和动作验证状态。不打扰写明 run/活动或在途触发时间及 HEAD。已交付用户线程也逐条列 link，空环境数量取数组实数。

首次或环境集合变化附环境对照表；开头写模型档位与依据。固定「例行复核」引用 checks：失败处理、监听、命名、久审清单各总数及成功/跳过/失败数；issue 编码回读与修复数。队列恢复附取消/保留/失败/剩余数，未知不写 0。

交接、等待空位、settle、久审审计单列，写来源与去向或依据；已定案记结论、授权/规则来源与执行状态；规则缺口记「建议改技能」，不靠跨轮承诺补规则。

「需要你决定」只列必须由用户提供的授权、产品取舍、互斥的用户要求或无法从环境核实的交接身份。每条写清所缺的用户输入、选项、默认保持状态与依据；技术方案、修在哪个 PR、复审次数及尚在运行的顾问任务不列入。取证/工具失败、额度不足或重复推进无效另列「阻塞」：证据、已做补救、下一责任方与可观察的恢复条件；仅当恢复确实需要用户操作时才转入「需要你决定」。实际未测、仅豁免、审查者缺席、仅启动等状态照实保留。
