# 故障恢复

失败、queued 超过 30 分钟、或需要换模型时读取。先核最新 run，已恢复运行的线程回主流程判定。

## 失败恢复

`failedThreads` 每条都处理，含 `source:"filtered"`；缺 task/tail 时恢复要点用「继续你被中断的工作」。用户主动取消、用户已定案保留或正在自行处理的线程保留原状并记依据。其余连续两个 failed、额度或上下文耗尽按下节换档发 M4；瞬时失败发 M12。调用失败先归因，不能仅凭失败次数认定额度耗尽。

## 模型优先级

四个环境共用同一订阅的额度池，一个环境耗尽，其他环境也一样——判定和换模型都全局看一次，不逐环境试探。

- 模型阶梯的唯一事实源是 [model-ladder.json](model-ladder.json)；快照顶层回带 `modelLadder`。新建线程、换模型、建探测都只准从本轮快照的 `modelLadder` 逐项取 `instanceId`/`model`/`options`；没有快照就先读这份文件。凭记忆写模型名、写到 `modelLadder` 之外的实例，都按「没重读技能」处理，立刻改用当前值重发。批量恢复失败线程优先跑 `<技能目录>/scripts/patrol-tier.mjs --snapshot <快照> --to <档位序号/name/fallback> --delay-ms 0` 完成换档、M4 与初次回读，再按主流程验证对应 run；先 `--dry-run` 核清单，用户取消、已定案保留、任务书指定模型的条目用 `--skip <id|link|title>` 排除，`cancelled` 默认跳过。
- **档位每轮独立判，不继承上一轮**：本轮与上一轮均无额度失败，就按首选档可用；上一轮有额度失败、本轮没有时走下条回升探测。上一轮切过档不是继续用低档的理由。
- **判「某档不可用」要当轮取证**：本轮探测或同档多条连续失败的报错已证实额度耗尽。单次瞬时失败、同模型其他线程却正常 → 不是额度问题，别换档。
- **探测只用来回升档位，不用来阻塞恢复**：上一轮确有额度（`model_usage_exhausted`、quota）失败、本轮还没新失败时，先建极简探测线程确认首选档是否恢复（标题 `额度探测`，任务只写「回复一句 ok 即可，不要做别的」，建在当前项目且不建工作树），确认探测 run 结束后当轮 settle（或归档）；探测是巡检自建临时线程，属于无 PR 用户线程保持原状规则的例外。本轮 `failedThreads` 已有多条同档且报错证实额度耗尽的失败，它们就是证据：不建探测、不判定等待，直接按 `modelLadder` 换下一档并逐条重发；若补救仍因同类额度失败，记录未恢复、下一可用档候选与恢复条件，列为阻塞；确需用户变更账号或授权才提问；同一线程本轮补救次数按主流程上限。
- 报错先归因再换档：`API 返回了 HTML 页面而不是 JSON` 这类是调用路径/凭证问题（Fast Ship 要带 `/api/` 前缀），不是模型坏；把现象扣到模型头上会白白切掉一整档。`413 Request Entity Too Large` 是该线程上下文超出路由的请求体上限，不是额度：只给这一条改用兜底档，档位判定不受影响。秒级失败（发起后约 1 秒内结束）连续两个档都这样，先查路由/上下文错误；证实请求体超限时仅该线程换兜底档重发，回读验证后再判恢复是否成功。
- 任务书或项目约定指定了模型时以任务书为准，巡检不替它换。
- 报告开头写一句本轮用的模型档位及依据（探测结果或本轮额度失败）。

## 队列恢复

queued 超过 30 分钟是补查信号。先读最新 `activeRunId`、recentRuns 与 `t3_queue action:list` 的全部分页：有活跃 run 就核进展；没有活跃 run 才调查排队项。

1. 对拟取消项逐条 `read`：确认是系统生成的 PR 状态通知，且对应 PR 最新 HEAD、reviews、comments、checks 可重新读取并覆盖其内容。记录 queuedRunId、来源、PR、覆盖依据。用户指令、附件、无法识别或含未被覆盖信息的项保留。
2. 取消前刷新线程与队列；若已有活跃 run，回主流程判定。只对本轮核过且仍 queued 的 ID 执行 `cancel`。逐项记成功/失败，不对 list 返回项无条件全部取消。
3. 回读剩余队列。全部阻塞项均已安全取消、仍无活跃 run 时，发一条「【巡检】队列中的陈旧 PR 通知已清理，请重读 <PR URL> 的最新状态，按账本继续」；保留了无法判定的阻塞项则报告证据缺口与恢复条件，只有需要用户辨认原意或授权时才列选项，不越过它们追加恢复消息。
4. 按 [发送与动作验证](../SKILL.md#4-发送与动作验证)核对启动。成功启动只能证明本次恢复有效；报告分别写取消数、保留数、失败数与剩余数，调度故障根因另查。
