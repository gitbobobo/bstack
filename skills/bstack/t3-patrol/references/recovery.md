# 故障恢复

失败、queued 超过 `thresholds.queuedMinutes`、或需要换模型时读取。先核最新 run，已恢复运行的线程回主流程判定。

## 失败恢复

`failedThreads` 每条都处理，含 `source:"filtered"`；缺 task/tail 时恢复要点用「继续你被中断的工作」。用户主动取消、用户已定案保留或正在自行处理的线程保留原状并记依据。工作区准备报错先走下节「工作树准备失败」，其余连续两个 failed、额度或上下文耗尽按「模型优先级」换档后发「【巡检】已切换模型到 <model>，继续：<一句恢复要点>」；瞬时失败发「【巡检】继续」。调用失败先归因，不能仅凭失败次数认定额度耗尽。

## 工作树准备失败

先区分工作区 provision 失败与代理 run 失败。`t3_thread_send` 只续跑代理；重发消息、fetch 成功或 `worktreePath` 非空都只能作为恢复线索。核当前工具是否提供准备重试；没有时记明接口缺口，由目标线程按可用的 `t3_worktree_handoff` 恢复绑定。工作区就绪前只做取证和恢复。

恢复完成标准：准备状态 ready、绑定路径及分支可用，且恢复后的对应 run 已在该工作区出现实际任务活动；随后再失败或续跑仍排队，仍记未恢复。一次补救后仍失败，按既有授权决定重建或报告阻塞。获准重建时先核旧 run、队列与子任务并停止重复执行，再用 `t3_thread_launch` 绑定新工作树，或以 `existing_worktree` 接管已核实可用且无活跃写入者的工作树；按当前接口参数执行，带齐原任务、来源及后续段。新线程通过上述验收后，把接手证据交 [结案门槛](handoff.md#结案门槛) 审批旧线程与交接来源。

## 参数兼容

配置、续跑或委派请求报 `Unknown option`、`rejected options`、选项非法取值时，先按 [t3-orchestrator 参数兼容](../../t3-orchestrator/references/failures.md#参数兼容)核目标环境目录、同模型本轮纠参及回读；此分支先于模型不可用与额度换档。快照 `modelLadder` 仍决定实例和模型，仅允许按该分支调整本轮 options，不修改持久阶梯，不记 `quotaFailure`。

只有旧日志、已恢复成功或本轮未用到该档时，报告历史错误和维护依据即可，不为检查参数新建探测任务；真实恢复被阻塞时才执行一次纠参重试。建议写明出错环境、实际支持项及验证结果，不把某目标拒参写成 Devin 全局不支持。权限/指定档位无法兼容才列明确约束，普通默认参数的兼容修复不转成用户决策。

## 模型优先级

四个环境共用同一订阅的额度池，一个环境耗尽，其他环境也一样——判定和换模型都全局看一次，不逐环境试探。

- 模型阶梯的唯一事实源是生效配置的 `modelLadder`，决策包与快照都带它。新建线程、换模型、建探测、派子代理都从中逐项取 `instanceId`/`model`/`options`（options 拒参只走上节「参数兼容」）；凭记忆写的模型名一律改用当前值。换档恢复写成两个调用：先 `t3_thread_configure`（`modelSelection` 取该档），再发上节的继续消息；用户取消、已定案保留、任务书指定模型的线程跳过。
- **档位每轮独立判，不继承上一轮**：「上一轮有没有额度失败」取快照的 `lastRound.quotaFailure`，不凭对话记忆。本轮与上一轮均无额度失败，就按首选档可用；上一轮有额度失败、本轮没有时走下条回升探测。上一轮切过档不是继续用低档的理由。
- **判「某档不可用」要当轮取证**：本轮探测或同档多条连续失败的报错已证实额度耗尽。单次瞬时失败、同模型其他线程却正常 → 不是额度问题，别换档。
- **探测只用来回升档位，不用来阻塞恢复**：上一轮确有额度（`model_usage_exhausted`、quota）失败、本轮还没新失败时，先建极简探测线程确认首选档是否恢复（标题 `额度探测`，任务只写「回复一句 ok 即可，不要做别的」，建在当前项目且不建工作树），回读探测线程，确认 run 已结束且完整活动无设备操作后当轮 settle（或归档）。如发现设备操作，按 [settle 前核设备锁](handoff.md#settle-前核设备锁) 处理。探测是巡检自建临时线程，不是用户线程，不适用用户线程保持原状的规则。本轮 `failedThreads` 已有多条同档且报错证实额度耗尽的失败，它们就是证据：不建探测、不判定等待，直接按 `modelLadder` 换下一档并逐条重发；若补救仍因同类额度失败，记录未恢复、下一可用档候选与恢复条件，列为阻塞；确需用户变更账号或授权才提问；同一线程本轮补救次数按主流程上限。
- 报错先归因再换档：`API 返回了 HTML 页面而不是 JSON` 这类是调用路径/凭证问题（Fast Ship 要带 `/api/` 前缀），不是模型坏；把现象扣到模型头上会白白切掉一整档。`413 Request Entity Too Large` 是该线程上下文超出路由的请求体上限，不是额度：只给这一条改用兜底档，档位判定不受影响。秒级失败（发起后约 1 秒内结束）连续两个档都这样，先查路由/上下文错误；证实请求体超限时仅该线程换兜底档重发，回读验证后再判恢复是否成功。
- 任务书或项目约定指定了模型时以任务书为准，巡检不替它换。
- 报告开头写一句本轮用的模型档位及依据（探测结果或本轮额度失败）。

## 队列恢复

queued 超过 `thresholds.queuedMinutes` 是补查信号。先用 `patrol-evidence.mjs --queue --thread <id>@<env> ...` 一次取齐各线程的 `activeRunId`、recentRuns 与全部排队项全文（系统 PR 通知已标 `prNotice`）：有活跃 run 就核进展；没有活跃 run 才调查排队项。

1. 对拟取消项逐条核对（`--queue` 已给全文，`truncated` 为真时再 `t3_queue action:read`）：确认是系统生成的 PR 状态通知，且对应 PR 最新 HEAD、reviews、comments、checks 可重新读取并覆盖其内容。记录 queuedRunId、来源、PR、覆盖依据。用户指令、附件、无法识别或含未被覆盖信息的项保留。
2. 取消前刷新线程与队列；若已有活跃 run，回主流程判定。只对本轮核过且仍 queued 的 ID 执行 `cancel`。逐项记成功/失败，不对 list 返回项无条件全部取消。
3. 回读剩余队列。全部阻塞项均已安全取消、仍无活跃 run 时，发一条「【巡检】队列中的陈旧 PR 通知已清理，请重读 <PR URL> 的最新状态，按账本继续」；保留了无法判定的阻塞项则报告证据缺口与恢复条件，只有需要用户辨认原意或授权时才列选项，不越过它们追加恢复消息。
4. 取消与恢复消息按顺序写进同一条研判的 `calls`，由 `patrol-round run` 执行并回读启动。成功启动只能证明本次恢复有效；报告分别写取消数、保留数、失败数与剩余数，调度故障根因另查。
