# 技术收敛

审查轮次越线、审计后仍复发、顾问意见分歧，或实现线程把方案与 PR 范围交回用户时读取。实现线程对技术结果负责，巡检负责让它进入正确的处理分支。

## 预算收口

先核当前 HEAD 上未关闭意见的级别，以目标线程 pr-review-loop 的「分级」为准，审查者标的 P2/Note 不等于 blocker：

- **只剩非 blocker**（其他路径、罕见边界、Note、已记录的 should）：发 M2，要它停止修复、逐条回复后按「结束」收尾；有收尾授权时它直接走 pr-finish。审查者状态只因这些意见为红时，按它的 pr-review-loop 请复核一次；仍红且合并入口拦截，记外部阻塞交给用户。
- **仍有 blocker**：按下文定位失败在哪，在原预算内修；审计不追加预算。

**完成标准**：线程已收到对应指令，或已记录它正在按同一指令收尾。

## 先定位失败在哪

回读上次顾问结论、对应 SHA、后续有效意见及实际 diff，区分：

- **执行缺口**：方案尚未落地、接线遗漏、描述声称修复但源码没有。指出具体缺项，M1 要求补齐；需要重新确定实施步骤用 M7。已有方案尚未验证前，不再派顾问重复选择同一路径。
- **方案反例**：方案已落实但可复现失败仍成立，或相同不变量持续被旁路。M14 让实现线程把新反例、失败测试、前次结论和未交付范围交顾问重新判断，并由实现线程选择与实施修正。
- **外部阻塞**：顾问调用、环境或依赖不可用。核任务是否实际启动或已有结果，按编排规则恢复；仍不可用写阻塞与恢复条件，不把运行故障包装成技术选项交给用户。

**完成标准**：指出哪项结论被哪份源码或反例否定，责任在实施、方案还是环境；同一次复审或修正已在执行时，只记录其进展。

## 根因处理

只针对仍未关闭的 blocker，目标是在预算内推进到可合并并按授权完成合并。清单持续减少时继续修复；出现同根新反例、反向修复或范围扩张时转入根因处理。实现线程依据原任务和顾问意见，确定职责边界、兼容约束、修正方案及验证计划并直接实施：

1. 用失败测试或可执行复现固定已确认反例，修正后验证；多次「声称修了未落地」时，提供父提交失败、修正提交通过的证据。
2. 拆分依据职责及依赖关系；保留原任务要求与安全不变量。换 PR、改名或拆提交保留同一方案的审查历史，非 blocker 遗留按 `$pr-review-loop`「分级」自主接受并记录，重大风险须解决，不能借拆分绕过。
3. 技术分歧由实现线程比较反例与验证证据，优先长期干净、职责清楚的方案，记录取舍后执行。顾问给出多个方案仍须实现线程选定；缺事实时先做窄实验，不能以「顾问也拿不准」结束技术责任。
4. 按选定路径继续实现、验证和增量验收，保留未解决意见和完整轮次历史。单纯等待最新 HEAD 的在途门禁不触发重设计；满足合并条件且已有授权时继续收尾到 MERGED。

**完成标准**：账本与 PR 描述写清被否定的假设、选定方案、保留范围、反例证据和下一验证动作；源码与验证证明修正已落实。仅派顾问、得到建议或重开配额都未完成此步。

## 用户决策边界

实现线程处理技术路径与保持原需求的 PR 边界。只有方案需要改变用户可见行为、放弃原任务目标、接受超出自主处置范围的重大风险或执行超出授权的动作，才依 SKILL.md 的权限与产品决策规则判断是否需用户决定；提问必须点明缺失的产品/授权输入，不能只列技术方案名称。

顾问仍在运行时，报告「复审中」及对应任务证据。线程自设「交回用户」或主动 unwatch 不构成用户暂停；按最新工作状态补监听并推进技术处理。用户明确暂停则保持暂停。
