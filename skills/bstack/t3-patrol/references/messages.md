# 回话模板

发给子线程的消息正文。触发条件以 SKILL.md 和相应分支文档为准；这里仅维护消息正文。

- 一律以 `【巡检】` 开头；`t3_thread_send` 带该环境的 `environmentId`、`mode:"auto"`。
- `<...>` 换成实际内容，其余照发；这些模板是代用户回话的口径，不自行增删要求。
- 模板里点名「不要等我确认」的地方是刻意的：这些线程常把该做的步骤挂起来等人批。

## M1 收敛路径未落地

> 【巡检】收敛路径没有落地：你在 <审计时间> 做过方向审计，但 <PR 描述仍没有「交付范围」／仍在逐条修范围外意见，择实写>。请回到你账本里的顾问定性，由你直接执行，不要等我确认：本轮内按 pr-review-loop 把交付范围写进 PR 描述、撤回未经准入的范围外改动、在账本记下收敛路径，然后再处理审查意见；范围外意见先按「改动准入」分流，不自动另开 PR

## M2 预算收口

> 【巡检】审查预算核对：<PR> 已 <N> 轮、开了 <时长>，当前 HEAD 未关闭意见：<级别与条数>。请按 pr-review-loop「预算」「分级」自己复核每条：意图外的路径、罕见边界、所有 Note 一律按 nit 一行回复、不改代码；只剩 nit/wrong/已记录的 should 就停止修复，回复完按「结束」收尾，有收尾授权直接走 $pr-finish。仍有 blocker 才修，在原预算内完成；同一 blocker 修两轮仍复发时按 pr-review-loop 的方向审计处理。不要等我确认

## M3 空转打断

> 【巡检】已核实无有效进展并打断：<重复活动及日志/结果证据>。请先查明为什么反复卡在这里，再做一个可验证的下一步，按结果继续；有效的长任务保留正常验证流程

## M4 换模型后继续

> 【巡检】已切换模型到 <model>，继续：<一句恢复要点>

## M5 同意按原任务继续

> 【巡检】同意，按原任务继续，后续同类步骤不用再问

## M6 遗留项分流

> 【巡检】测试遗留沿用 pr-review-loop「测试失败处置」；其余逐项按「改动准入」分流：已准入且查重后的独立缺陷才立项，本需求必须交付的后续段才写交接提示词，候选记重启条件，不采纳项写依据。账本里的 nit 不默认转成新任务，没有已准入后续段就写「无后续段」并继续收尾

## M7 技术取舍按根治

> 【巡检】先按 pr-review-loop「改动准入」核对待办与原需求，再按账本或 PR 中已有的顾问定性执行；没有或出现新反例时，请方向顾问独立分析（`route.mjs select --task design` 选人），由你确定保持需求的方案与 PR 边界，记录证据后实施。blocker 出现同根新反例或反向修复时转入根因处理，保留跨 PR 审查历史；产品方向缺授权则保留原行为交用户决定，技术选项由你负责

## M8 没关联 PR

> 【巡检】本线程尚未关联 <PR URL>。请用 `link_pull_request` 关联 <PR URL>，核对并用 `watch_pull_request` 补齐审查与 CI 监听（工具不在列表里先用 tool_search 搜一次），然后立即重读最新审查意见与检查状态，按 pr-review-loop 继续

## M9 处理未消费的审查结果

> 【巡检】当前 HEAD 上还有未处理的审查结果：<HEAD、意见/结论出处>。请重新读取最新审查意见与检查状态，按 pr-review-loop 继续，核对并补齐监听

## M10 收尾

> 【巡检】使用 $pr-finish 技能收尾

## M11 审查者复核超时

> 【巡检】<审查者>的复核似乎没回来（触发已过 X 分钟）。请通过该 PR 宿主的检查接口确认最新 HEAD 状态，按 pr-review-loop 账本核对重试次数和等待上限；允许重试才重触发，达到放弃条件则记为「审查者缺席，结束等待」，再核未解决意见、检查与验收条件决定是否可收尾

## M12 瞬时失败继续

> 【巡检】继续

## M13 索要交接提示词

> 【巡检】请按 pr-review-loop「改动准入」区分遗留候选与本需求必须交付的后续段；只有已准入后续段才按仓库约定给完整交接提示词、来源依据及目标设备，否则写「无后续段」并列候选的重启条件

## M14 顾问复审收敛路径

> 【巡检】收敛路径执行后仍未收敛：你在 <审计时间> 做过方向审计，之后又过了 <轮次> 轮、新增 <条数> 条意见。请把账本、上次定性和这几轮意见交给一位方向顾问复审（`route.mjs select --task design` 选人，与上次不同模型家族）：上次编号清单的哪项预测被新证据否定、是否需要改判或调整交付范围；轮数沿用账本，不追加预算。请你依据复审意见选定根因修正方案，落实源码修正与反例验证，写进账本和 PR 描述后继续；顾问尚在运行就报告进展。清单在减少就继续修复；出现同根新反例或反向修复就调整机制，技术路径由你负责确定，按 pr-review-loop 的分级只修 blocker、其余记录，合并另按已有授权执行，不等我确认

## M15 产品取舍分流

> 【巡检】现有需求与文档未确定 <具体产品取舍>。先按 pr-review-loop「改动准入」分流：可选改进默认保留原行为、记候选或不采纳，继续原任务并收尾，不等待用户；只有完成原任务必须作此决定时，才写清缺失决定、选项、推荐项及影响交用户选择，独立且已授权部分继续。技术实现仍由你结合顾问意见自主决定，顾问不替用户扩展产品需求

## M16 资源可能已释放

> 【巡检】资源可能已释放（<依据：该设备占用从 N 降到 M／已等待 X 小时>）。请按 t3-orchestrator「资源不足时」重新检查，够用就继续；仍不够就更新 `【等待资源】` 后结束本轮

## M17 无 PR 收尾回收

> 【巡检】任务已按原任务验收完成、没有后续段，进入收尾回收：请核对工作树里没有待交付的改动（有就提交推送或说明去向），验收结论和必要证据写进对应 issue 或文档，删除本任务另建的辅助工作树并 `git worktree prune`；共享的服务、容器和缓存不动。做完回一句「可回收」，列出证据去向。工作树本身在 settle 后由回收脚本清理

## M18 后台进程随超时被杀

> 【巡检】你用来启动后台验证的命令以超时结束，后台进程已随进程组一起被杀：<bgKills.sample>，共 <count> 次，最近一次 <lastAt>。这不是内存或调度问题。请改用所在 harness 自带的后台模式重启这一步（输出写日志文件），按 pid 或 cwd 跟进自己的进程；此前把这类被杀归因到内存、调度器或测试编排的记录（账本、PR、issue、定时任务提示词）一并更正，然后继续原流程

## 无模板的两类

- **产品口径核对**：原任务或 issue 有已确认答案时，消息写「结论 + 依据出处 + 要它执行的动作」，格式自由；仅有审查者/顾问建议不算已确认答案，找不到依据用 `M15` 区分可选建议与原任务必需决定。
- **停滞推一把**：按尾部所指的那条规则选模板（M1–M18），不另写。
