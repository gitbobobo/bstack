# 跨设备切片

多平台、合并问题或部分范围受阻的候选，在决定设备与准入时读本篇。切片是可独立实现、验证与合并的交付范围，不是按标题的平台词过滤整条问题。

## 1. 划边界

读完整正文与共识，把范围分成「本机可交付」「后续设备接力」「仍受阻」。逐项核：

- **能力**：从仓库设备分工列出本机允许修改的客户端、共享层与工具链，以及可用验证入口。按模块职责判断：其他客户端消费的共享代码也可能在本机职责内；用同一种语言写的另一端宿主代码则仍受设备分工约束。
- **闭环**：本段合并后保持兼容，所需前置已完成，并有生产消费者或可独立验收的基础设施收益。共享层先行可连同本机客户端接入形成闭环，剩余端串行接力；只有定义、没有消费者或独立收益的空接口不算交付。原子跨端改动或必需验证只能在别机完成时，写具体耦合点，不用“全端需求”代替依据。
- **取证**：正文没提供现成切片时，定向查最新目标分支的定义、调用方、测试入口或前置状态，直到能指出本段闭环或不可拆的依赖。目录词、历史行号、旧扫描结论只是线索；“核心切片证据不足”须附已查路径及仍缺的事实，否则保持待核。
- **决策**：技术设计、接口方案、测试组织由执行线程按仓库顾问流程解决；派活前核清需求、当前问题、交付边界与可行验证，不预先代做完整实现设计。用户可见的语义取舍仍按准入找授权，缺必需产品决定时才阻塞对应范围。
- **准入**：本段仍须通过主技能的准入。架构统一须有真实漂移、契约冲突或明确需求，不能只靠“更深、更统一”立项。扫描清单里的行为缺陷、产品取舍与死代码删除分别分诊；实现线程在最新基线上核实引用与可达性，再按证据改动。

**完成标准**：有一段能独立验证、合并的范围，或有明确不能切片的依赖依据；仅出现其他平台名称不足以跳过。并行候选按共享契约、模块与验证资源核冲突：基础纯函数与其上的会话重构有依赖时串行或合入同一线程；不同问题编号、各有空位不代表可以并行。

## 2. 一个来源，一个接力负责人

同一来源问题本轮只建一个执行线程，沿用整项认领与查重，不把同一 ID 分给多台设备绕开台账。将以下任务约束写入计划 `reason`（会进入任务书），标题标出本段：

- **本段**：允许修改的模块、交付物与验证要求。
- **边界**：本段不实施的范围、兼容要求；合并来源里的其他编号列为核对线索，只有确为重复且本次一并覆盖的问题才放进 `ids` 认领。
- **接力**：剩余范围、目标设备及前置；本段合并后由本线程按 t3-patrol [交接与 settle](../../t3-patrol/references/handoff.md) 交接，受阻时进入待交接队列。
- **结项**：本段完成只更新进度与证据，来源保留进行中；全部范围完成后，最后接力线程核总验收再关闭来源。

**完成标准**：任务书同时有本段验收与剩余责任归属，不能把“本机这段完成”表述成整项完成。
