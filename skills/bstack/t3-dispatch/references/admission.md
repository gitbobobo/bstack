# 独立任务准入

挑选自动派活候选、重新评估历史遗留或将可选交接转为独立任务时使用。本页判断“这个任务是否值得、能否执行”；`pr-review-loop` 判断“本 PR 该改什么、何时停止”。审查级别与原 PR 的预算不作为派活门槛；同一未完成交付换 PR 续办仍保留原审查历史。

## 按任务目标取证

1. **目标与价值**：从问题正文、用户共识和当前源码核清要改善什么。缺陷修复核受损场景与已有复现线索；功能需求核期望行为；架构、测试、文档与体验改进核当前维护成本或使用收益。架构扫描和审查意见均可提供候选，按任务自身价值判断。
2. **交付与验收**：圈定可独立交付的范围、必须保持的行为和可行验证。技术方案、复现调查和测试设计由执行线程完成，派活前无需代做完整设计或先拿到失败测试。缺少足以确定目标与范围的信息时，列具体待核查询。
3. **授权与可执行性**：核用户明确否决或暂缓、必需产品决定、前置依赖、设备能力及同范围在途工作。原 PR 将意见记为 nit、接受不修或排除某范围，只说明那次交付的处置；用户明确撤销该目标才构成停止依据。优先标签按 labels.md 执行。
4. **投入与排序**：比较预期收益、迁移与验证成本、回归风险。通过后按主流程的优先级与容量派出；架构类排序靠后不等于不可派。收益不足时写具体权衡，而不是仅凭来源类型或无故障判退。

## 架构改进的证据

重复策略、多处同步修改、边界类型泄漏、职责混杂、隐式状态顺序或验证困难，都可形成独立技术目标。指出相关路径和依赖，说明拟减少的维护负担、保持的契约及验收方式，例如策略收成单一实现、依赖方向可检查、状态转换显式化且行为检查保持通过。结构改进无需先证明用户故障；只有声称修复具体 bug 时才核对应缺陷证据。

## 判定与完成标准

- **可派**：目标与价值明确、交付和验收可行，授权与执行条件具备；技术设计交实现线程推进。
- **硬阻塞**：写明未完成前置、必需用户决定、缺失信息或承担同一切片的线程。
- **待核**：尚不能判断，保留最小查询；取证预算用完记筛选未完成。
- **不推荐**：已解决、重复、用户否决，或具体收益不足以覆盖投入与风险，记录依据及适用的重启条件。

每条候选留下目标、关键依据和上述结论。独立任务按自己的交付目标接受后续 PR 审查；不把原 PR 的 nit 身份带成新任务的拒绝理由，也不因登记过“后续”自动认领执行。
