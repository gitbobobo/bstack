# 资源不足时

巡检只按名额派活，不替你看磁盘和负载：这台机器上同时有几个线程在构建，空间够不够，由你在用到时自己查。读这篇的时机：要跑或要派重验证之前——全量构建、门禁、E2E、截图、生成器。单 crate 的 check/test、lint、改代码都不用查。

## 检查

在工作树根跑：

```bash
node <t3-orchestrator 技能目录>/scripts/resource-check.mjs --need <GB>
```

- `--need` 是这一步预计新增的占用。仓库文档写了构建体积就按文档；没写就看本工作树或同仓库其他工作树已有的构建产物大小（`target`、`.build`、`node_modules`、`DerivedData` 等），取保守值。只跑已构建过的增量检查可以填 0。
- 输出的 `verdict` 为 `go` 才开跑（退出码 0）；`wait`（退出码 3）时看 `disk`（`short`：跑完会低于保底）和 `load`（`busy`：CPU 繁忙）。
- 放行后照常经仓库的调度入口或编译槽排队；排了很久才轮到时，开跑前再查一次。

## 不够时按顺序处理

1. **先做不吃资源的步骤**：改代码、补测试、定向轻量检查、写 PR 描述与账本。重验证挪到最后，这些做完再查一次。
2. **磁盘不够时回收一次**：带 `--reclaim` 重跑。它只删已终结线程留下的孤儿工作树和保留工作树里可重建的构建产物（判定交给 t3-code 的 `t3-worktree-gc.mjs`），不动在用的工作树。别的线程的目录和进程不归你处理。
3. **仍不够就停下**：本轮最后一条消息的第一行写成固定格式，然后结束本轮：

   ```
   【等待资源】<磁盘|负载>：剩 <X> GB，需 <Y> GB（负载写 CPU <Z>%）；已完成：<做完的步骤>；恢复后：<下一步>
   ```

   巡检认这个标记：这台设备暂停派新任务；设备空出名额或等待满几个小时后，巡检会发「【巡检】资源可能已释放」叫醒你。醒来先回到「检查」。

子代理遇到资源不足时把检查结果回报给你，由你按上面的顺序决定，不让子代理自己停在等待上。
