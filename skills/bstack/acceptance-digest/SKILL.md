description: 从近 24 小时各项目合并的 PR 里挑出需要用户亲自验收的，汇总为一份按项目分组的网页。用户要验收清单、或定时任务点名时使用。

巡检按授权用审查与自动化证据替代人工验收，把需求推到合并；本技能是它的对立面：回看合并结果，把**只有用户本人能验收**的 PR 交还给他，其余的不打扰。你的读者是那位只想花几分钟、只看要紧事的用户。下文 `<技能目录>` 指本技能目录，产物都在 `/tmp/acceptance-digest/`。

## 1. 收集

```bash
node <技能目录>/scripts/digest.mjs collect [--hours 24] [--repo <host/owner/name>]...
```

仓库缺省取 bstack 派活与巡检配置里登记的全部项目；用户点名项目或时间窗时用 `--repo`、`--hours` 覆盖。脚本把每个窗口内合并的 PR 写进 `prs.json`：标题、描述、最近评论、文件清单与增删行数，`waiverHints` 摘出正文或评论里验收豁免、实体设备未测的原句。

**完成标准**：每个仓库有合并数或 `error`；`error` 原样带进最终报告。

## 2. 判定

逐个读 `prs.json` 里的 PR，归入 `accept`（需验收）或 `skip`（免验收）。符合下列任一条就是 `accept`：

- **用户可感知**：新功能，界面、交互、文案、通知、默认值或对外接口的变化，且自动化证据替代不了亲眼看一遍。截图已证实的一眼小改（错字、间距）归 `skip`。
- **代答取舍**：PR 或评论写了假设、暂定、取舍、待确认，或实现与 issue 原文有出入——代理替用户做了产品决定。
- **证据缺口**：`waiverHints` 非空，或合并后仍有待办的验证（「合并后以 tag 验证」），或改动的价值在体感上（外观、动效、音频、性能、手感）。
- **主路径重写**：播放、同步、登录、存储等核心链路的大范围重写，即便声称行为不变，也给一条冒烟路径。
- **高风险面**：数据迁移与删除、支付计费与权益、认证权限、发布与分发配置、外部服务集成。改了行为或重写了链路的标 `risk: "high"`。

其余归 `skip`：局部重构、测试、文档、CI、依赖升级、日志、内部工具，以及有回归测试覆盖、难以手动复现的缺陷修复，各写一句理由。

描述不足以写出验收步骤时，读 PR 的 diff 或关联 issue 补齐（GitHub `gh pr diff`，Forgejo 取 PR 的 `.diff` 地址）。`accept` 项的写法：

- `summary`：用用户的话说改了什么，一两句，不写文件名。
- `why`：命中了哪一条、具体缺什么证据。
- `checks`：1–4 条可直接照做的步骤，写清入口、操作与预期结果（「设置 → 播放 → 打开交叉淡入，切歌时两首重叠约 3 秒」）；验收对象是已合并的主分支或最新构建。
- `evidence`（可选）：已有的测试、截图、审查结论，让用户知道哪些不必再看。

判定写成 `/tmp/acceptance-digest/verdicts.json`：

```json
{
  "projects": {
    "github.com/owner/name": {
      "accept": [{ "num": 12, "risk": "normal", "summary": "…", "why": "…", "checks": ["…"], "evidence": "…" }],
      "skip": [{ "num": 13, "reason": "…" }]
    }
  }
}
```

**完成标准**：每个合并的 PR 恰好出现在一个 `accept` 或 `skip` 里；每条 `checks` 都能让没读过代码的人照做并判断通过与否。

## 3. 发布

```bash
node <技能目录>/scripts/digest.mjs publish /tmp/acceptance-digest/verdicts.json
```

脚本先核对判定覆盖了每个 PR，缺项时列出并退出码 1，补齐后重跑。有待验收项时，用 [网页模板](assets/page.html) 生成一份 `acceptance.html`，经 html-preview 上传一次（有效期 7 天）；侧边栏按仓库分组。退出码 2 表示缺 html-preview 配置，按 html-preview 技能的首次使用流程配好再跑。只需本地预览时加 `--dry-run`，用报告给出的本地路径。

**完成标准**：有待验收项时输出一个总览链接或本地路径；每个仓库都有一行状态（待验收、全部免验收、无合并或取数失败）。

## 4. 汇报

以脚本报告为底稿回复用户：先给唯一的总览链接和总待验收数，再按项目列待验收数，并逐条点名高风险 PR（`#编号 标题：为什么要看`）。取数失败的仓库原样注明错误。所有仓库取数成功且都无需验收时，只回一句窗口与合并总数。
