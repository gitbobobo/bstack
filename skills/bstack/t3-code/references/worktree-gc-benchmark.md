# 工作树快清理基准

## 真实慢路径与第二轮修复

本机历史 `wtgc.log` 中，两个旧工作树共执行 36 次 `git cherry`，全部在约 15 秒超时，仅 cherry 累计 540.402 秒；超时后仍遍历各远端分支生成 diff、patch-id 和 log。日志记录的命令耗时共 772.437 秒。这是首轮小型夹具没有覆盖的真实慢路径，不能用下文的小夹具提速比例宣称它已解决。

第二轮调整：所有模式的交付验证共享截止窗口，默认整次 10 秒、每树最多 5 秒，fetch 与提交图/patch 命令共用剩余时间，apply 复查不重置。超时/失败立即保留该树，不继续比较；祖先检查合为一次 Git 遍历，patch 深度比较只查上游/默认分支，最多两个候选。已因脏源码、珍贵文件、索引问题阻断的树默认不再联网验证。

### 同输入超时回放

新增 `t3-worktree-gc.verify.test.mjs`：真实 Git/SQLite 夹具中造出大量 origin 分支，只在 child_process 边界将 cherry 注入历史同类 ETIMEDOUT，省去真实的每次 15 秒等待。

- 修复前运行 `node --test --test-name-pattern='超时即止' .../t3-worktree-gc.verify.test.mjs`：断言失败，实际调用 20 次 cherry，而不是预期的 1 次。
- 修复后：只调用 1 次 cherry，随后 skip，不继续 diff/log；另测预算跨树、跨 apply 复查共享，及 fetch、祖先检查、diff、log、patch-id 各阶段超时后保留目录。
- 这是重试放大的可重复回归，不将注入的瞬时超时解释为真实墙钟提速比例。

### 本机真实目录复测（只预演，不删除）

Windows / Node v24.15.0，第二轮源码执行：

| 命令范围 | 墙钟时间 | 结果 |
|---|---:|---|
| 默认全盘 `--purge-build` | 12.411 秒 | 检查 22 个目录，已删 0，cherry 调用 0 |
| 对历史两个慢树 `--disposable --path ... --path ...` | 5.619 秒 | 两树均保留，已删 0，cherry 调用 0 |

定向复测中 archived origin 的 fetch 约 4.959 秒超时，立即保留第一树，第二树复用失败记录、不重试；没有再进入逐分支 cherry。超时后核查该调用时间窗口内的 git/SSH/HTTP 子进程，无残留。预演不改工作区文件，但 fetch 可能更新远端跟踪引用。

当前目录/网络/线程快照与历史日志不同，因此不把历史 772 秒和这次墙钟时间作为严格同输入倍率；本次证明的是实际预演已能结束、失败不会再逐分支放大。预算也不代表整个 GC 的墙钟上限：目录扫描、占用检查和物理删除不计入该窗口。

### 第二轮回归验证

推送前最终源码：GC 主套件 26 项（25 通过、1 项 POSIX 限定在 Windows 跳过），预算/超时套件 6 项、资源回收调用方 5 项，相关测试合计 36 通过、1 跳过。整合最新 origin/main 后，完整仓库 `node scripts/check.mjs` 通过：20 个技能、18 个测试文件全绿，退出码 0；语法检查及 `git diff --check` 通过。

推送前独立审查补出了普通树后代绑定与定向收尾范围两处边界问题：新增两项测试先复现删除活跃嵌套树/无关空目录，再修复为所有整树操作都保护后代绑定、分组清理只处理本轮已删目标的父目录并刷新保护检查。两模型审查收敛；另单独修复既有 patrol-state 测试使用 URL.pathname 导致的 Windows 路径错误。

主套件要求整个大型夹具都清完的 apply 用例显式使用 60 秒总窗口；默认窗口耗尽后必须保留的行为由独立预算测试验证，而非要求默认预算内清完整个目录森林。

## 首轮：小型依赖目录基准

2026-11-12，Windows / Node v24.15.0。基线：`d7a4003051d3b4eb49219ee8831da7ac293b2d8f` 中的 `scripts/t3-worktree-gc.mjs`（Git blob `cf48652638abb1e041abbbaba431b4470eb2c3e5`）。

## 方法

运行 `scripts/t3-worktree-gc.bench.mjs --baseline <旧脚本绝对路径>`，使用真实 Git 和 SQLite，不 mock 命令。每个样本独立建 3 棵已终结线程的链接工作树，每树 50 个源码文件和 4,000 个 ignored 依赖文件，共 12,000 个 ignored 文件。origin 为本地 bare 仓库。每种模式 3 轮，轮换执行顺序，夹具创建不计时，删除真实执行并断言全部目标已删。

- baseline：旧保守 GC，全量 dry-run 后 apply。
- fast：`--disposable`，相同全量目标直接 apply；仍验证远端。
- delivered：对每棵树分别 `--disposable --path <树> --delivered-head <SHA> --apply`；免联网验证，包含三次进程启动的成本，删除量不变。

为比较扫描成本，fast/delivered 也测 dry-run，但新工作流不包含这一步。所有 apply 均在一次 dry-run 后测量，因此属于温缓存对比，不是冷盘延迟。未测试真实网络、大型仓库、数百万文件、杀毒软件差异或后台删除队列；不将此结果外推为真实机器 GC 的绝对耗时。

## 结果

单位秒，各列独立取中位数，不能将前两列相加当作最后一列。

| 模式 | dry-run | apply（含实际删除） | 日常工作流 |
|---|---:|---:|---:|
| baseline | 0.898 | 2.324 | 3.103 |
| fast | 0.751 | 1.905 | 1.905 |
| delivered | 0.526 | 1.380 | 1.380 |

最终源码复测：相对旧工作流，fast 耗时减少约 **39%**，delivered 减少约 **56%**。只比较 apply，分别减少约 **18% / 41%**；工作流其余收益来自取消重复预演。所有模式清理同量目录，尚未计入日常定向回收避免扫描其他工作树的收益。三树共享仓库时，日志中的 fetch 次数从旧工作流的 5 次减到 fast 的 1 次、delivered 的 0 次。
